# 계정 발급 절차 (SPEC-PILOT-LAUNCH-001 M3, REQ-PILOT-LAUNCH-005)

> 이 문서는 운영자가 `scripts/provision-tester.ts`(`pnpm tester:add`)로
> **계정을 발급**하는 절차와 주의사항을 다룬다. 파일럿 **운영 중** 장애
> 대응 절차는 `.moai/docs/pilot-incident-runbook.md`를 참고한다(둘은 서로
> 다른 문서다).

## 1. 스크립트는 프로덕션을 자동으로 감지하지 않는다

`scripts/provision-tester.ts`의 `buildDb()`(24-27행)는 실행 시점의
`TURSO_DATABASE_URL` 환경변수 값으로 접속 대상 DB를 그대로 구성한다.
스크립트 내부에는 "지금 프로덕션에 연결하려는가"를 판단하는 로직이
전혀 없다 — 환경변수가 로컬 파일을 가리키면 로컬에, 원격 Turso를
가리키면 그 원격 DB에 그대로 계정을 발급한다. 어느 DB에 쓸지는 전적으로
**실행 환경의 환경변수 설정**에 달려 있다.

## 2. 발급 전 확인 절차 (필수)

계정을 발급하기 **전에** 아래 두 가지를 반드시 확인한다.

### 2-1. 대상 DB 호스트 확인

```bash
echo "$TURSO_DATABASE_URL"
```

- `file:`로 시작하면 로컬 SQLite 파일이다 — 프로덕션이 아니다.
- `libsql://` 또는 `https://`로 시작하고 예상한 프로덕션 Turso 호스트명과
  다르면 **즉시 중단**한다. 기대한 호스트명과 정확히 일치하는지 눈으로
  대조한다.
- `TURSO_AUTH_TOKEN` 값은 어떤 경우에도 로그, 커밋 메시지, 대화창 등에
  출력하거나 붙여넣지 않는다.

### 2-2. `BETTER_AUTH_SECRET` 일치 확인

로컬에서 계정을 발급하면서 실수로 Netlify 프로덕션과 다른
`BETTER_AUTH_SECRET`을 사용하면, 발급된 계정으로 프로덕션에서 로그인이
실패한다(세션 서명 불일치). 발급 전 로컬 `.env` 파일의
`BETTER_AUTH_SECRET` 값이 Netlify 대시보드의 Production 환경변수 값과
**정확히 일치**하는지 확인한다.

## 3. 알려진 제약 — 재실행 시 조용한 무연산(no-op)

이미 존재하는 이메일로 스크립트를 재실행하면, 기존 사용자 조회에서
일치 항목을 찾아 **아무 것도 하지 않고 조용히 반환**한다
(`scripts/provision-tester.ts` 139-147행 `existing.length > 0` 분기).
이때:

- 비밀번호는 **재설정되지 않는다** — 새로 지정한 비밀번호는 무시된다.
- 스크립트는 오류 없이 성공한 것처럼 종료된다(exit code 0).

같은 이메일로 비밀번호를 바꾸고 싶다면, 이 스크립트가 아니라 별도의
비밀번호 재설정 경로를 사용해야 한다(이 문서가 다루는 범위 밖).

## 4. 비밀번호·비밀값 기록 금지

이 문서(그리고 이 절차를 인수인계하는 어떤 메모·이슈·채팅 기록에도)에는
실제 비밀번호나 `TURSO_AUTH_TOKEN`, `BETTER_AUTH_SECRET` 같은 비밀값을
**절대 그대로 기록하지 않는다**. 예시가 필요하면 항상 자리표시자를
사용한다.

```bash
pnpm tester:add -- --email <email>
# Password: <password>   ← 실제 값 대신 항상 이렇게 표기
```

## 5. 발급 후 검증 — exit code 0만으로는 부족하다

스크립트가 exit code 0으로 종료했다는 사실만으로 "발급 완료"라고
단정하지 않는다. §3의 무연산 케이스처럼, exit code 0은 "새로 발급됨"과
"이미 있어서 아무 것도 안 함" 두 경우를 구분하지 못한다.

발급 후에는 반드시 **실제 프로덕션 로그인 화면에서 발급한
이메일/비밀번호로 직접 로그인을 시도**해 확인한다. 로그인이 성공해야
비로소 발급이 의도한 대로 완료된 것으로 간주한다.
