## 한 줄 소개

보상레이더는 보험설계사와 손해사정사가 비식별 보험 사건 정보를 입력하면, 상해후유장해·질병후유장해 관점에서 추가로 검토할 담보·근거자료·반대 논리·추가 필요자료를 조사해 주는 B2B AI Research Assistant다.

## 타깃 사용자

- **보험설계사** — 고객 사건을 접수한 뒤 놓친 담보가 없는지, 추가로 준비해야 할 자료가 무엇인지 빠르게 점검하고 싶은 실무자.
- **손해사정사** — 상해후유장해/질병후유장해 사건을 조사·심사하면서, 자신의 판단을 뒷받침하거나 반박할 근거자료를 폭넓게 확인하고 싶은 실무자.
- B2B 전용 도구이며, 개인(B2C) 보험 가입자를 대상으로 하지 않는다.

## 핵심 기능

### 1. 접근 제어 (비공개 파일럿)
보상레이더는 공개 서비스가 아니라, 사전에 지정한 실무자 10명 내외를 대상으로 하는 비공개 파일럿이다. 회원가입은 없고, 운영자가 사전에 등록한 테스터 계정만 로그인할 수 있는 초대 전용(allowlist) 방식을 채택한다. 모든 사건(case) 레코드는 생성한 사용자 계정에 귀속되며, 다른 테스터의 사건 데이터를 조회할 수 없다. 구체적인 인증 방식은 `tech.md`, 라우트/미들웨어 구조는 `structure.md` 참고.

### 2. 사건 입력
사용자가 비식별화된 보험 사건 정보(상해/질병 경위, 진단명, 장해 부위 등)를 입력한다. 주민번호, 전화번호, 상세주소, 의료기록 원본 등 민감정보는 애초에 입력받지 않는다. 이 원칙은 선언에 그치지 않고, 사건 입력 폼/API의 입력 검증 스키마(Zod)가 해당 필드 형식(주민등록번호 패턴, 전화번호 패턴 등)을 구조적으로 거부하는 방식으로 실제 코드에 강제한다 — 자세한 내용은 `structure.md`의 `lib/validation/` 항목과 `tech.md`의 Zod 항목 참고.

### 3. 리서치 파이프라인
입력된 사건은 다음 단계를 거쳐 리서치 리포트로 변환된다.

```
사건 입력
  → CaseNormalizer   (입력을 표준화된 사건 구조로 정규화)
  → QueryPlanner      (검토가 필요한 쟁점·검색 쿼리를 계획)
  → Evidence Retriever (근거자료 후보를 수집)
  → Researcher         (수집된 근거를 바탕으로 검토 소견을 작성)
  → Skeptic             (작성된 소견에 반대 논리·허점을 제기)
  → Verifier             (Researcher와 Skeptic의 결과를 evidence 대비 교차 검증)
  → Research Report        (최종 리포트 생성)
  → 전문가 피드백 저장         (실무자의 평가·수정 의견을 축적)
```

각 단계는 독립적으로 교체·개선 가능하도록 분리되어 있으며, 최종 산출물은 항상 근거자료(evidence)와 연결된 형태로 제공된다.

### 4. Research Report
- 추가로 검토할 담보 목록
- 각 담보별 관련 근거자료
- 예상되는 반대 논리(보험사 측 주장 가능성 등)
- 추가로 확보해야 할 자료 목록

리포트는 결론이 아니라 "무엇을 더 봐야 하는가"를 제시하는 리서치 보조 자료다.

### 5. 전문가 피드백 저장
실무자가 리포트에 대해 남긴 평가·수정 의견을 저장한다. 이는 향후 파이프라인 품질 개선의 기초 데이터가 된다.

## MVP 범위 경계

이번 MVP는 다음 두 담보 영역만 지원한다.

- **상해후유장해**
- **질병후유장해**

그 외 담보 영역(질병사망, 실손의료비 등)은 이번 범위에 포함하지 않는다.

## 핵심 원칙

1. **AI는 지급 여부·확률을 단정하지 않는다.** 보상레이더는 "보험금이 나온다/안 나온다"를 판단하는 도구가 아니라, 검토가 필요한 지점을 짚어주는 리서치 보조 도구다.
2. **모든 주요 AI 판단은 evidence와 연결한다.** Researcher·Skeptic·Verifier가 내리는 판단은 근거자료 없이 독립적으로 존재하지 않는다.
3. **개인정보·민감정보 저장을 최소화한다.** 주민번호, 전화번호, 상세주소, 의료기록 원본은 MVP 단계에서 아예 받지 않는다. 이는 입력 검증 스키마(Zod, `lib/validation/`)가 사건 입력 폼/API 경계에서 해당 필드 형식을 구조적으로 거부하는 방식으로 강제되며, DB나 LLM에 도달하기 전에 차단된다.
4. **초대 전용 비공개 접근.** 셀프 가입은 없으며, 운영자가 사전에 등록한 테스터 계정만 로그인할 수 있다. 모든 사건 레코드는 생성한 사용자 계정에 귀속되고, 다른 테스터의 사건 데이터는 조회할 수 없다.
5. **seed 데이터 우선.** 초기에는 대규모 실데이터 수집보다 작은 seed evidence 데이터셋으로 end-to-end 파이프라인을 먼저 완성하는 것을 우선한다.
6. **LLM 종속 방지.** 특정 LLM(Gemini 등)에 애플리케이션 로직이 종속되지 않도록 AI provider abstraction을 둔다.
7. **DB 이식성.** DB는 Drizzle ORM 뒤에 두어, 향후 PostgreSQL로 이전 가능한 구조를 유지한다.
8. **불필요한 overengineering을 하지 않는다.** microservice, Kubernetes, 별도 vector DB 등은 이번 MVP에서 도입하지 않는다.
9. **작은 실사용 검증이 목표다.** 현직 실무자 10명 각각이 최소 3건의 사건 리서치 사이클을 완료하고 전문가 피드백을 제출하는 것을 이번 단계의 성공 기준으로 삼는다.

### 후속 개발 (파일럿 실측 데이터 확보 이후, 순서 있음)

파일럿 실행 자체(테스터 모집·초대·실제 사용)는 SPEC-PILOT-READY-001의 범위가
아니며, 그 실행이 안전하게 가능해지도록 준비하는 것까지만 다룬다. 파일럿이 실제로
진행되어야 아래 항목들의 우선순위를 데이터 기반으로 판단할 수 있다 — 다음 순서를
전제로 한다:

1. **실 Gemini 기반 코퍼스 품질 평가** — 대표성 있는 사례 표본에 대해 실제 Gemini로
   코퍼스 품질을 평가(예: `counterEvidenceIds`가 항상 빈 배열인 현상의 원인 규명)
2. **사용자별 완료/피드백 집계 대시보드** — ①의 데이터를 바탕으로 완료 현황·피드백
   집계를 보여주는 관리자 뷰
3. **Gold Dataset 추출·집계 도구** — ①②로 축적된 원시 피드백 행을 실제 골드
   데이터셋으로 추출·가공(SPEC-FEEDBACK-001에서 이미 후속 SPEC으로 명시적으로
   미뤄진 항목)
