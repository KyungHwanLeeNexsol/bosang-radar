# LSP-RULES-1 구현 보고: 실행기·Windows 러너·관리자 진입점·판정·시험 (스텁·모의 검증만)

- 작성일: 2026-10-30
- 기준: PR #40 HEAD `3e06c458851a8cc583bcc7ad19d40056c95be529` 위의 별도 브랜치 `security/semgrep-lsp-rules-load-exec`. 이 브랜치로 별도 Draft PR을 올리며 기존 PR(#40 포함)은 바꾸지 않았다.
- 성격: **구현과 스텁·모의 검증까지다.** 실제 Semgrep은 `--help`·`--version`을 포함해 한 번도 실행하지도 임포트하지도 않았고, 계정·방화벽·감사·ACL 같은 시스템 격리도 적용하지 않았다. 규칙 다운로드, 대상 스캔, 음성 대조, 병합, 배포도 하지 않았다. `pin.json`(diff 0줄), `verified`, `policy_accepted`, ADR 상태, 기존 PR, `main`, 보담 저장소는 그대로다.
- 이 문서가 말하지 않는 것: 실제 Semgrep 1.180.0이 `initialized` 뒤에 어떻게 동작하는지, 프로브 규칙이 실제로 유효한 규칙으로 해석되는지, 로딩된 규칙의 개수와 의미(탐지)가 어떤지. 이 구현은 그것들을 관측하지 않는다.

### 3.4 계획의 두 정정

- 공용 `settings.ts`: `auto`·`r2c`·`policy`·`supply-chain`·`hooks`(정확히 일치)와 `r/`·`p/`·`s/`·`http://`·`https://`(접두어)를 대소문자 구분 없이 거절한다. 로컬 상대 경로(`semgrep-rules/javascript`, `./rules`, `rules/hooks-dir`)와 기존 호출부 두 곳(`harness.ts`, `lsp-min.ts`)의 계약은 그대로다. 통과·거절 표를 시험으로 고정했다.
- 드라이브 문자로 시작하는 절대 경로 요구는 `lsp-rules.ts`(`isDriveAbsolute`)와 러너 요청 검사에만 있고 `settings.ts`에는 없다.
- `NOT_ATTEMPTED`는 서버를 띄우지 않았을 때만이다. 띄운 뒤의 신원·결합·해시 실패는 실행 사실을 남긴 채 `NOT_OBSERVED`이며 시험으로 고정했다.

## 4. 검증 환경

- Windows 11 Home 10.0.26200 한 대. Windows PowerShell 5.1.26100.9711과 PowerShell 7.6.9, Node v24.22.1, vitest 4.1.11.
- 진짜로 실행된 것은 **무해한 스텁 서버, 임시 디스크, 루프백**뿐이다. 러너와 스텁은 현재 사용자로 돌았다.
- 계정·방화벽·감사·ACL·Security 로그는 모의로만 시험했다. 단, 시험 중 몇 개 구역은 이 PC의 상태를 **읽기 전용으로** 읽는다: 관리자 시험의 "진짜 상태 불변 확인"(개발 중 기본 설정으로 여러 번 돌았고, 회귀·최종 실행부터는 `-SkipRealStateCheck`로 건너뛰었다), 기존 `Test-IsolationScripts.ps1`의 `Get-Acl` 실패 관측. 읽기뿐이며 바꾼 것은 없다.
- 새 시험은 러너가 실제로 도는 엔진인 **Windows PowerShell 5.1 호스트**로 돌렸다. PowerShell 7이 띄운 5.1 자식은 7의 `PSModulePath`를 물려받아 `Get-FileHash`가 인식되지 않는 일이 있었다(개발 중 실제로 겪음). 그래서 러너는 안전 판정용 해시를 .NET 구현으로 덮어쓴다(`lsp-min-runner.ps1`은 바꾸지 않음). 기존 `Test-LspMinAdmin`·`Test-VersionFlows`·`Test-IsolationFlows`는 `param` 기본값의 `$PSScriptRoot` 때문에 5.1 호스트에서 부를 수 없어(기존 시험의 성질) README 절차대로 `pwsh` 호스트와 `-Engine powershell`로 돌렸다.

## 7. 변이 점검 (핵심 방어에 한정)

변이는 파일을 백업하고 정확히 한 번만 나오는 문자열을 바꾼 뒤 시험을 돌리고, 항상 복원해 해시로 확인했다. 끝에 변이 대상이던 38개 파일의 sha256 목록이 변이 전과 같음을 비교했다(의도한 수정 파일 제외).

**TypeScript 31건 중 28건 잡힘, 3건 생존.** 잡힌 것: `initialized` 게이트 우회 3가지(응답 무효·버전 불일치·초기화 오류 로그), 두 번째 `initialized` 허용(기록 쪽은 행동 시험이, 실행기 쪽은 구조 시험이 잡음), 맨줄 4개·프로브 로딩 짝 조건 제거, 괄호 깊이 추적 제거, `NOT_ATTEMPTED` 확대 2가지, 프로브 해시 null 허용, 서버 요청 상한 3 이상 3가지, 장벽 뒤 감시 제거 2가지, 우선순위 뒤집기, `settings.ts`의 `hooks`·`policy` 제거, F5·F6a·F2·F3·F4·F6c 되돌리기, 일치 토큰·OS 차단 검사 제거.

| 생존 변이                                                       | 처리                                                                                                                                                                                                                                             |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| M6a 설치물 해시를 전후 모두 읽지 못함(null=null)                | **시험이 없던 방어이고, 새 시험이 빈 문자열끼리도 일치로 읽히는 실제 결함을 드러냈다.** 해시가 null·빈 문자열이면 "읽지 못함"으로 보도록 고쳤다(`hashUsable`). 시험 `G1`이 변이 재적용 시 실패함을 확인했다                                      |
| E5 관리자 문맥의 `hashesUnchanged`가 없거나 불리언이 아님       | 시험이 없었다. 시험 `G2`를 추가했고 변이 재적용 시 4건 실패함을 확인했다                                                                                                                                                                         |
| M7 알 수 없는 `stderrBytesAtSend`를 0으로 읽음(F1 되돌리기)     | 조건 3이 같은 입력에서 이미 `INITIALIZED_OFFSET_UNKNOWN`으로 성공을 막으므로 **판정은 변하지 않는 동등 변이**다. 시험을 더하지 않았다                                                                                                              |

**PowerShell 4건 중 3건 잡힘.** 서수 비교를 `-ceq`로 되돌림(21건 실패), 만들기 전 링크 검사 제거(2건 실패), `initialized` 게이트를 두 곳 모두 우회(16건 실패). 게이트 두 곳 중 **한 곳만** 우회한 변이는 직접 관련된 시험이 실패하지 않았다. 러너에는 같은 게이트가 첫 판단과 드레인 뒤 재확인으로 두 군데 있어 한쪽이 다른 쪽을 막아 주는 동등 변이이기 때문이다(그 실행에서 실패한 1건은 아래 8절의 타이밍 시험이다).

한계: 변이는 위 방어에 한정했다. 전체 변이 점검이 아니다. 두 번째 `initialized` 차단은 실행기 쪽에서 행동 시험이 아니라 구조 시험이 잡는다.

## 9. 미확인 사항과 한계

1. **실제 바이너리 동작은 한 번도 관측하지 않았다.** `INFO`·`WARNING` 머리말 형태, 두 경고 줄의 실제 문구, 맨줄 4개의 실제 출력은 소스에서 도출한 예측이다. 문구가 다르면 판정은 `NOT_CONFIRMED`로 끝난다(성공이 되지 않는다).
2. 프로브 규칙의 유효성, 로딩된 규칙의 개수·의미, 소스와 설치된 바이너리의 대응은 계획 보고서 8절 그대로 미확인이다.
3. 실제 전용 계정·방화벽·감사·ACL 아래의 러너 동작, 실제 `Start-Process -Credential`, 실제 Security 로그의 5157 형식은 시험하지 못했다(모의).
4. 닫힌 덤프 안의 금지 문구는 신호로 세지 않는다(요구 사항에 따른 의도). 끝에서 닫히지 않은 블록만 성공을 막는다. PS 로그 판독기는 `openBlockAtEnd`를 구현하지 않는다(최종 판정은 TS가 원문 바이트로 다시 하므로 영향은 러너의 실시간 판단에 한정).
5. F10~F13(6절)은 고치지 않았다.
6. 시간에 민감한 시험이 있다. 전체 상한 시험(`전체 상한이 장벽 한도(60초)보다 먼저 닿으면 …`)은 스텁이 1.2초 안에 `initialize`에 응답한다고 가정한다. 변이 점검 중 한 번 부하로 흔들렸다(다른 실행에서는 통과). 재현되면 한도 값을 키워야 한다.
7. 개발 중 `bodam` 안의 에이전트 작업 폴더 4개는 처음부터 있던 것이며 새로 만들지 않았다.
8. Windows 11 한 대, 엔진 두 가지(5.1·7), 전용 비관리자 계정 한 개 가정.
