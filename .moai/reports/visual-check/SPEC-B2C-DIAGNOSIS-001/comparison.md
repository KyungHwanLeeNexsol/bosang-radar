# 시각 정합성 비교 — SPEC-B2C-DIAGNOSIS-001 (D2 9차, 2026-09-21)

**이 문서는 이전 버전("D2 8차")을 갱신한다.** 8차가 세운 게이트 구조는
그대로 두고, 남아 있던 줄바꿈 검사 공백 두 곳을 채운 뒤 **문서가 적어 둔
검증 범위를 스크립트 실제 설정과 대조해 정정했다**(§7). 이 문서의 수치는
전부 이번 라운드의 전체 10화면 실행이 다시 측정한 값이다.

## 1. 이번 라운드가 바꾼 것

8차는 §7에 "줄 수만 검증한 여러 줄 요소"로 M01 안내 배너와 M01-A2 설명
두 건을 남겨 뒀다. 이번 라운드는 그 두 건을 줄바꿈 **지점**까지 검사하도록
올렸고, 올리자마자 8차가 PASS로 기록했던 실제 결함이 또 드러나 함께 고쳤다.

그리고 그 과정에서 **§7의 기술 자체가 스크립트보다 느슨했다는 것**이
확인됐다 — 두 건 모두 "줄 수만 검증"이라고 적혀 있었지만 실제 설정에는
`expectLines`도 `expectLineTexts`도 없었다. 검증기가 실제 줄 수를 출력에
기록하긴 했어도 판정에 쓰이는 값은 아니었으므로, 줄 수가 달라도 통과하는
상태였다. 이번에 문서의 수치를 코드에서 다시 세어 맞췄다.

| 8차에 남아 있던 것 | 9차의 조치 | 그래서 드러난 것 |
|---|---|---|
| M01 안내 배너·M01-A2 설명에 줄 게이트 자체가 없음 | 두 요소에 `expectLines` + `expectLineTexts`를 함께 추가 → 지점 대조 **8 → 10건** | M01-A2 설명이 디자인보다 한 글자 일찍 끊김 |
| §7이 두 요소를 "줄 수만 검증"으로 기술 | 실제로는 둘 다 `expectLines`조차 없었다 — 설정과 문서를 함께 정정 | 문서·코드 수치 불일치 |
| 동의 설명 문구의 가운뎃점 앞뒤 공백 누락 | 디자인 실측으로 확인 후 Desktop·Mobile 모두 정정 | 그 문구로 역산한 **글자 크기 값까지 오염**돼 있었음 |
| "내용 보기" 뒤 꺾쇠 없음 / 배너 아이콘이 삼각형 | 디자인대로 꺾쇠 추가, 방패형 경고로 교체 | 꺾쇠 추가가 동의 행 라벨 줄바꿈을 유발 → 트리거 여백 결함 노출 |

## 3. 측정 방법론

1. **프로덕션 캡처 강제**: 캡처 대상은 항상 `next build` + `next start`다.
   매 화면 캡처 직전 `page.locator("nextjs-portal").count() === 0`을 단언해
   개발 서버 캡처를 차단한다(10개 화면 전부 0).
2. **동일 좌표계·동일 알고리즘**: 2배 해상도 디자인 export를 Chromium
   `<canvas>`에 50%로 그려 1배로 정규화하고, 구현은 디자인과 정확히 같은
   1배 viewport로 캡처한 뒤, 같은 ink-pixel 세그먼트 함수를 두 이미지에
   적용한다.
3. **요소 식별과 측정의 분리**: 구현 쪽은 DOM locator로 요소를 *식별*하고,
   그 DOM 영역 안의 *잉크*를 측정한다.
4. **저대비 상자용 2차 임계값**: 옅은 테두리·옅은 배경 상자는 임계값 6을
   디자인과 구현 양쪽에 동일하게 적용한다.
5. **애니메이션 정지**: `reducedMotion: reduce` + 캡처 직전
   `animation: none / transition: none / caret-color: transparent` 주입.
6. **단계 상태 고정(01-C/M01-C)**: `?devStep=loading&devStage=1`로 단계를
   고정한 뒤, 세 행의 상태 문구가 `완료 / 진행 중 / 대기`임을 DOM에서 직접
   확인하고 캡처한다. 이 고정 동작 자체는 이번 라운드에 Vitest 7건으로
   검증했다(§8).
7. **배경색 측정(8차 신설)**: 화면 전체 최빈색은 배경색의 대리값으로 쓸 수
   없다 — 흰 카드 면적이 회색 배경과 비슷해지면 실제 배경이 그대로여도
   최빈색이 뒤집히고, 반대로 콘텐츠 아래쪽만 색이 달라도 최빈색은 그대로다
   (7차 M01-C가 전자였고, 그 뒤에 후자인 실제 결함이 숨어 있었다).
   그래서 **콘텐츠가 침범하지 않는 좌우 가장자리 8px 세로 띠**만 디자인·구현
   동일 방식으로 재고, ① 디자인 쪽 균일도(프로브 영역 설정 검증) ② 구현 쪽
   균일도 ③ 색 일치(채널당 ±1) 셋을 모두 게이트한다.
8. **측정 공백 = FAIL(8차 신설)**: DOM은 찾았는데 잉크 박스가 안 나오거나,
   오버레이 화면의 밝은 박스 크롭이 실패하면 위반으로 기록한다. 화면 PASS
   판정도 "그 화면이 만든 위반 0건"이라는 단일 규칙으로 바꿔, 요소별 pass
   플래그에 반영되지 않는 위반이 새는 경로를 없앴다.
9. **측정 축**: 요소마다 `left / top / width / height` 4축 + 줄 수 +
   (지정한 요소는) 줄바꿈 지점 + 상태 문구 + 화면 배경색. 의미가 달라지는
   항목(상태 문구·문구 원문·줄바꿈 지점·배경색)은 픽셀 허용 오차와 무관하게
   일치해야 한다.

판정은 Desktop Δ ≤ 8px, Mobile Δ ≤ 4px의 **이진 PASS/FAIL**이다. "PASS
근접"·"PASS(경계)" 같은 완화 범주는 코드에도 이 문서에도 존재하지 않는다.

### 8차 기술 정정

먼저 용어를 갈라 둔다. 검증기는 **모든** 요소의 실제 줄 수를 측정해
출력(`measurements.json`)에 기록한다. 그러나 그 값이 PASS/FAIL을 가르는 것은
`expectLines`가 설정에 있을 때뿐이다. 즉 **"출력에 기록된다"와 "게이트로
동작한다"는 별개**이며, 아래 "줄 수조차 검사하지 않았다"는 후자를 뜻한다.

| 8차 §7의 기술 | 실제 |
|---|---|
| "M01 안내 배너 — 줄 수만 검증" | **정정.** 설정에 `expectLines`도 `expectLineTexts`도 없었다 — 줄 수는 기록만 됐을 뿐 판정에 쓰이지 않았다. 9차에 두 게이트를 함께 추가했다 |
| "M01-A2 설명 — 줄 수만 검증" | **정정.** 이쪽도 마찬가지로 둘 다 없었다 — "줄 수만 검증"은 실제보다 엄격하게 읽힌 기술이다. 9차에 두 게이트를 함께 넣었고, 넣자마자 한 글자 어긋남이 드러났다(§8) |
| "01 카드 그리드·01-D 안내 패널·M01 칩 영역·M01 카드 목록·M01-C 단계 행 — 줄 수만 검증" | **정정.** 이들은 `expectLines`가 없다 — 줄 수도 검사하지 않는다. 여러 자식이 모인 컨테이너라 `mergeBands`로 **밴드를 묶어 바깥 상자만** 대조한다(설정 10곳). "줄 수만 검증"이라는 표현이 실제보다 엄격하게 읽혔다 |

## 8. 이번 라운드(9차)에 바로잡은 실제 결함

1. **동의 설명 문구의 가운뎃점 앞뒤 공백**(Desktop·Mobile 공통). 디자인은
   `사고 · 질병 · 치료`인데 구현은 `사고·질병·치료`였다. 눈으로는 판단하기
   어려워 디자인 export의 가운뎃점 좌우 공백을 실측했다 — **6.5px**로,
   공백 없는 가운뎃점의 좌우 여백(약 2.2px)보다 뚜렷이 크다. 같은 화면의
   안내 배너 제목·히어로 설명은 이미 공백 표기를 쓰고 있어 이 문장만
   어긋나 있었다.

2. **그 문구로 역산한 글자 크기 2건**. 7차가 구한 Desktop 설명 14.35px은
   공백이 빠진 문자열로 잰 값이었다 — **문구 결함이 크기 값까지 오염시킨
   경우다.** 공백 있는 문자열로 다시 재면 디자인 잉크 폭 371px에 맞는
   크기는 13.83px이다(고친 뒤 폭 Δ0). Mobile 설명은 `text-sm`(14px)이
   한 번도 검증된 적 없었는데, 9차의 지점 검사가 `…처리됩` / `니다.`로
   디자인(`…처리됩니` / `다.`)보다 한 글자 일찍 끊김을 잡아냈다 —
   13.4px + 행간 21px로 맞췄다(폭 Δ2).

3. **"내용 보기" 뒤 꺾쇠 누락**. 디자인에는 있고 구현에는 없었다.

4. **안내 배너 아이콘**. 디자인은 느낌표가 들어간 방패인데 구현은 공유
   `Notice` 컴포넌트의 기본값인 삼각형 경고였다. 기본값은 그대로 두고
   진단 호출부에서 `icon` prop으로만 덮어썼다.

5. **동의 행 트리거의 좌우 여백**(3번이 드러낸 결함). 꺾쇠를 넣자 트리거가
   18px 넓어지며 왼쪽 라벨이 두 줄로 접혀 행 높이가 디자인 51px 대비
   62px이 됐다. 원인은 ghost sm 변형의 좌우 여백 10px로, 디자인에서는
   꺾쇠가 행 안쪽 오른쪽 끝(x=358)에 딱 붙는다 — 여백을 없애 위치를
   맞추자 접힘도 함께 풀렸다. Desktop도 같은 구조라 함께 고쳤다.

6. **Mobile 시트의 설명 수직 위치**. 행간을 21px로 잡으며 문단 상자가 2px
   자라 설명이 디자인보다 5px 위로 갔다. 시트는 아래쪽 고정 + 높이 auto라
   위쪽 여백만 늘리면 시트가 위로 자라 제목이 따라 올라간다 — 설명 위에
   5px을 더하고 동의 행에서 같은 5px을 빼 전체 높이를 유지했다.

**게이트 실증**: 이번에 추가한 두 줄바꿈 게이트는 실제로 결함을 잡아
exit 1을 냈다(위 2번). 회귀 테스트 4건도 구현을 일부러 되돌려 실패하는
것을 확인한 뒤 복구했다 — `progress.md`의 "D2 9차" 절에 기록했다.

## 9. 잔여 위험

- **`.pen` 원본 미접근**: 글자 크기는 동일 문자열의 잉크 폭에서 역산한
  값이라 재현 가능하지만, 디자이너가 지정한 정확한 값과 1px 미만 차이가
  있을 수 있다. `16.07px` 같은 소수점 값이 남아 있는 이유다.
- **M01-A2 설명의 줄바꿈은 경계에 걸쳐 있다(9차 신규)**: 이 문단은 폭
  358px에서 마지막 어절이 들어가느냐 마느냐가 1px 남짓으로 갈린다.
  잉크 폭에서 역산한 값(13.31px)은 문장 전체가 한 줄로 붙어 버리는 쪽
  경계(13.33px)보다 0.02px 낮게 나왔다 — 디자인 도구와 브라우저의 글자
  배치 차이가 그대로 드러나는 구간이다. 그래서 역산값을 그대로 쓰지 않고,
  줄바꿈이 디자인과 같아지는 구간(13.34~13.91px)과 폭 오차가 허용치 안에
  드는 구간(13.13~13.44px)이 겹치는 곳의 가운데인 **13.4px**를 골랐다
  (현재 폭 Δ2, 줄바꿈 여유 1.9px). 폰트 버전이나 브라우저 텍스트 배치가
  바뀌면 이 여유가 사라질 수 있다 — 다만 그 경우 `line-text` 게이트가
  조용히 통과시키지 않고 exit 1로 잡아낸다.
- **꺾쇠 트리거의 터치 영역**: 동의 행의 "내용 보기" 트리거는 디자인 위치를
  맞추느라 좌우 여백을 없앴다(§8 5번). 높이 28px·폭 약 65px로 44px 권장
  터치 타깃보다 작다 — 다만 여백 제거 전에도 높이는 28px였으므로 이번
  라운드가 새로 만든 문제는 아니다.
- **01-A2 제목의 측정 경계**: 이 요소의 잉크 박스에는 같은 높이에 있는
  닫기(X) 버튼이 함께 들어간다(디자인·구현 모두 동일). 따라서 이 행의 폭
  비교는 "제목 좌측 시작점 ~ 닫기 버튼 우측 끝"을 비교하는 것이며, 순수한
  제목 텍스트 폭만 비교하는 것이 아니다. M01-A2 제목은 이번에 핸들을
  밀어내며 이 문제가 해소됐다.
- **회전 애니메이션 요소**: 스피너는 애니메이션을 CSS로 정지시켜 기준 상태로
  고정했으므로 재현 가능하지만, 기준 상태의 호(arc) 모양이 디자인의 "C"
  형태와 완전히 동일하지는 않다(Δ는 허용 오차 이내).
- **질문 문구 의존**: M01-B 제목의 줄바꿈 지점 검증은 현재 placeholder 질문
  문구에 묶여 있다. 매칭 엔진 연결로 질문이 동적으로 바뀌면 이 검증 항목은
  갱신이 필요하다.
- **부분 실행이 이미지 산출물은 덮어쓴다**: `measurements.json`은 전체
  실행으로만 갱신되지만, `screenshots/`·`overlays/`·`diffs/`의 개별 파일은
  부분 실행도 그 화면 것을 갱신한다. 파일명이 화면을 밝히므로 혼동 위험은
  낮지만, `VISUAL_SKIP_BUILD=1`로 오래된 `.next`를 쓴 부분 실행은 현재
  소스와 다른 캡처를 남길 수 있다.
- **단일 환경에서만 재현 확인**: Pretendard를 실제로 로드해 폰트 의존성을
  제거했으므로 원리상 다른 OS/CI에서도 재현 가능하지만, 실제로 실행해
  확인한 환경은 Windows + Chromium 하나뿐이다.
- **커버리지 실측치 없음**: 이 워크트리·OS(Windows) 조합에서
  `@vitest/coverage-v8`가 0/0을 산출하는 환경 결함이 이번 라운드에서도
  해소되지 않았다. 시각 정합성 범위 밖이라 별도 조치하지 않았다.
