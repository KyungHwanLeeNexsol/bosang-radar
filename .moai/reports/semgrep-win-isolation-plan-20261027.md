# Windows 격리 준비: 설정·검증·복구 스크립트와 실행 계획

- 작성일: 2026-10-27
- 기준: PR #35 브랜치 `security/semgrep-lsp-dist-verify`의 정정 반영 HEAD `b18a57e` 위의 별도 브랜치 `security/semgrep-lsp-win-isolation`
- 성격: 스크립트와 문서 추가. **계정 생성, 방화벽 규칙, 감사 정책, ACL 변경, 전용 계정으로의 프로세스 실행은 한 번도 하지 않았다.** `semgrep`·`semgrep-core`·`pysemgrep`(`--version` 포함)도 실행하지 않았다.
- 이 문서는 격리 효과의 증거가 아니다. 효과는 `Test-IsolationEffect.ps1 -Execute`를 소유자 승인 뒤에 실행하고 그 관측을 읽어야만 말할 수 있다.
- **후속(2026-10-27):** 이 문서는 실행 전 시점의 계획과 근거 구분이며 아래 서술(예: "한 번도 하지 않았다", "미확인")은 그 시점 그대로 보존했다. 이후 이 PC에서 `-Apply`/`-Execute`/복구를 실제로 1회 실행했고 그 결과는 [실행 보고서](semgrep-win-isolation-run-20261027.md)에 있다. 이어서 전용 계정에서 `semgrep --version`을 1회 시도한 결과는 [버전 관측 보고서](semgrep-version-observation-20261027.md)에 있다.

### 3.3 실행하지 않아 모르는 것

- 계정 단위 `Block` 규칙이 이 PC에서 실제로 프로세스의 TCP 연결을 막는지, 부모가 띄운 자식에도 적용되는지.
- `LocalUser`에 넘기는 SDDL 문자열(`D:(A;;CC;;;<SID>)`)의 정확한 형식을 이 PC가 받아들이는지. 도움말은 "SID를 SDDL 문자열로 표현"이라고만 적고, 이 문자열 모양은 같은 문서의 `RemoteUser`·`RemoteMachine` 예시(`D:(A;;CC;;;SID)`)를 따른 것이다. `RemoteAddress` 범위 표기(IPv4 두 범위, IPv6 한 범위)는 도움말의 허용 형식과 같은 모양이지만, 이 PC가 받아들이고 읽을 때 같은 값으로 돌려주는지는 모른다. 적용 스크립트가 만든 뒤 읽어 확인하도록 했으나 아직 실행하지 않았다.
- 루프백이 규칙의 영향을 받는지. 규칙은 루프백 대역을 원격 주소 범위에서 빼서 만든다.
- 차단 시 5157이 기록되는지, 기록의 `ProcessID` 표기(십진수/16진수), `Application`의 NT 경로가 `QueryDosDevice` 대응으로 실행 파일 경로와 맞아떨어지는지.
- 실패 감사를 켠 동안 다른 프로그램의 차단 연결이 얼마나 쌓이는지(이미 가득 찬 순환 로그를 얼마나 더 빨리 밀어내는지).
- `Start-Process -Credential`로 띄운 프로세스의 권한·프로필 생성·백신/EDR 반응.
- UDP, ICMP, IPv6, DNS 질의의 차단 여부. DNS는 서비스(`Dnscache`)가 대신 질의하므로 계정 단위 규칙의 대상이 아닐 수 있다(추정, 미관측).

## 4. 설계

### 4.1 왜 계정 단위 규칙인가

PR #35 보고서 7.2절의 선택지 A(전용 계정 + 사용자 단위 아웃바운드 차단)를 구현한다. 프로그램 경로별 규칙은 `semgrep.exe`·`semgrep-core.exe`·`python.exe` 경로만 막고, 그 프로세스가 띄운 다른 실행 파일의 통신은 놓친다. 계정 범위 규칙은 그 계정의 토큰으로 도는 모든 프로세스에 적용되도록 한 것이 **설계 의도**이고, 실제로 그런지는 3.3절대로 미관측이다.

### 4.2 자원과 소유 확인

모든 자원 이름은 실행마다 새로 정해지는 `RunId`(`yyyyMMddTHHmmssZ-<8hex>`)에서만 나온다. 복구는 이 이름과 설명 표식(`bosang-semgrep-iso:<RunId>`)이 함께 맞는 것만 지운다.

| 자원         | 이름                                                    | 소유 확인(복구 때)                                           | 복구 동작                                        |
| ------------ | ------------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------ |
| 로컬 계정    | `bsi<8hex>`                                             | 이름 + 설명 표식 + 기록된 SID                                | 사용 중지 → 프로세스 종료 → 삭제(+선택 프로필)   |
| 방화벽 규칙  | `bosang-semgrep-iso-<RunId>-out`, Group `bosang-semgrep-iso` | 이름 + Group + 설명 표식                                | 삭제                                             |
| 작업 폴더    | `%ProgramData%\bosang-semgrep-iso\<RunId>`              | 위치 + `.owner` 파일 내용                                    | 삭제(루트는 우리가 만들었고 비었을 때만)         |
| ACL 항목     | 지정 경로에 새 계정 SID 한 건                           | 기록된 SID가 계정 SID 형식(`S-1-5-21-…`)일 것                | 그 SID의 ACE만 제거                              |
| 감사 설정    | "Filtering Platform Connection"(필요하면 "Process Creation") | 현재 값이 우리가 설정한 값일 때                         | 켜기 직전에 읽은 원래 값으로. 그 사이 바뀌었으면 건드리지 않고 `DRIFT` 보고 |
| 암호 파일    | RunDir의 `credential.dpapi`                             | -                                                            | 삭제                                             |

기존 계정, 기존 방화벽 규칙, 프로필 기본 정책은 읽기만 한다. 자체 점검이 `Set-NetFirewallProfile`·`Set-NetFirewallSetting` 호출이 없음을 구조로 검사한다.

### 4.3 감사 정책은 적용 때가 아니라 검증 동안만

Security 로그가 이미 가득 찬 순환 상태이고(3.2절), 실패 감사를 켜면 이 PC의 모든 프로그램의 차단 연결이 기록된다. 그래서 감사는 `Initialize`가 아니라 `Test-IsolationEffect.ps1 -Execute`가 **그 실행 동안만** 켜고, 끝나면 우리가 바꾼 값만 되돌린다. 원래 값은 켜기 직전에 `auditpol /backup`으로 새로 읽는다(사전 점검 시점의 값을 믿지 않는다). 지원하지 않는 값(0~3 밖)은 추측하지 않고 중단한다.

### 4.4 전용 계정의 파일 접근

3.2절대로 설치 경로가 모두 프로필 아래라서 새 비관리자 계정은 가상환경 `python.exe`도 기반 인터프리터도 읽지 못한다. 선택지는 둘이다.

1. `-GrantReadExecute`로 가상환경 폴더와 기반 Python 폴더에 **새 계정 SID 한 건의 읽기·실행 ACE**를 추가한다(기존 ACE는 그대로, 복구 때 그 SID만 제거). 기존 설치의 ACL을 바꾼다는 점이 비용이다. 적용 뒤 대표 하위 파일로 전파를 읽어 확인한다.
2. 접근 가능한 위치(예: `%ProgramData%` 아래)에 Python과 가상환경을 다시 설치한다. 배포물 재설치이고 이번 범위 밖이다.

기본값은 권한을 주지 않는 것이다. 이 묶음의 첫 프로브는 `powershell.exe`(시스템 폴더, 기본적으로 읽기 가능)를 쓰므로 ACL 변경 없이도 돈다. 가상환경 `python.exe`를 전용 계정으로 실행해 보는 것은 `-VenvPython`을 줄 때만 하고, 이것도 `semgrep`이 아니라 `python -I` 한 줄이다.

### 4.5 루프백

규칙의 원격 주소 범위에서 `127.0.0.0/8`과 `::1`을 뺀다(기본 `-RemoteScope NonLoopback`). Windows가 루프백을 방화벽 규칙에서 따로 처리하는지는 문서에서 확인하지 못했고, 규칙이 아니라 **프로브가 직접 관측**한다: 전용 계정이 루프백 수신기에 연결할 수 있어야 한다. 루프백 수신기의 수신 건수는 "OS 차단 관측"과 합치지 않고 별도 항목으로만 보고한다. 루프백에 0건이 찍혀도 외부 통신이 없었다는 뜻이 아니다.

### 4.6 "이번 실행의 차단"을 세는 방법

PR #35 보고서 7.3절의 절차를 코드로 옮겼다. 5157 이벤트는 다음이 **모두** 맞을 때만 이번 실행의 것으로 센다: ① `ProcessID`가 실행기가 CIM으로 기록한 부모·자식 PID 중 하나, ② `Application`의 NT 경로를 `QueryDosDevice` 대응으로 바꾼 값이 기록한 실행 파일 경로와 같음, ③ 이벤트 시각이 그 프로세스의 시작~종료 구간(앞 1초, 뒤 5초 여유) 안, ④ 방향이 Outbound. 목적지가 프로브와 같으면 프로브에 귀속하고, 다르면 "이번 실행의 다른 목적지"로 따로 센다. 하나라도 못 맞추면 "식별 불가"로 센다. 실행 직전 Security 로그의 마지막 레코드 번호를 기준점으로 기록하고, 이벤트는 그보다 큰 번호만 읽으며, 가장 오래된 번호가 기준점을 넘어서면 로그가 밀린 것으로 본다. 로그를 못 읽거나, 증거를 읽는 시점의 실패 감사 상태를 확인하지 못했거나(`null`), 꺼져 있었거나, 밀렸거나, 필수 프로세스 기록이 없으면 건수는 `null`이고 판정은 `FAILED_EVIDENCE_UNAVAILABLE`이다(0건이 아니다). 읽은 이벤트 수는 진단용 `unreliableCounts`에만 남긴다. 정상적으로 읽었고 감사가 켜져 있었고 밀리지 않았는데 맞는 이벤트가 없으면 빈 이벤트 목록도 예외 없이 처리되어 `FAILED_WITHOUT_OS_EVIDENCE`가 된다. 연결 실패만으로는 차단이라고 쓰지 않는다. 판정표는 `README.md`에 있다.

이 대조는 **프로브의 신원이 먼저 확인된 뒤에만** 한다(4.8절). 신원 확인에 실패한 실행에서는 이벤트를 이번 실행에 귀속하지 않는다.

### 4.7 계정과 암호

비관리자, Users 그룹만, 무작위 암호, 만든 직후 비활성화하고 검증 실행 동안만 켠다. 암호는 현재 Windows 사용자의 DPAPI로 `credential.dpapi`에 보관한다. 이 묶음은 사용자 권한 할당(로컬/네트워크 로그온 제한) 같은 시스템 정책을 바꾸지 않으므로, 계정이 켜져 있는 동안의 로그온 경로 제한은 하지 않는다. 그 점은 잔여 위험으로 남는다(6절).

### 4.8 프로브 신원 교차 확인, 이번 실행과의 연결, 정리의 구조

외부 검토에서 세 가지가 지적되어 고쳤다(9절).

- **신원.** 성공 판정에 쓰기 전에 서로 다른 출처를 맞춘다: 실행기가 CIM으로 직접 기록한 부모·자식 프로세스, 프로브가 스스로 쓴 파일, 부모가 보고한 자식 PID. 소유 SID = 전용 계정, 실행 파일 = 기대한 `powershell.exe`, 자식의 부모 PID = 부모 프로브, 자기 보고(PID·경로·SID·시작 시각) = CIM, 이번 실행 시작 이후에 떴는가, 보고한 종료 시각이 타당한가. 필수 기록이 하나라도 없거나 어긋나면 성공할 수 없고(`PROBE_ISOLATION_OBSERVED` 불가), 프로브가 쓴 연결 결과·시각은 검증된 사실로 쓰지 않으며 진단용으로만 따로 남긴다. 서명이나 출처 인증은 하지 않는다(이전 실행과 구분하는 값일 뿐이다).
- **이전 결과 파일.** 실행마다 `runToken`을 만들어 대상 목록과 프로브의 모든 결과 파일에 적게 하고, 시작 전에 이전 실행의 프로브 파일을 지우며, 토큰이 다른 파일은 존재해도 받지 않는다. 신원 확인도 토큰을 한 번 더 검사한다(두 겹).
- **정리.** 감사 단계는 설정을 시도하기 전에 호출자의 복구 목록과 실행 기록(`intent`)에 넣는다. 복구 결과는 `RESTORED` / `ALREADY_RESTORED` / `NOT_CHANGED` / `READ_FAILED` / `SET_FAILED` / `VERIFY_FAILED` / `DRIFT`로 구분하고, 되돌린 뒤 다시 읽어 원래 값임을 확인한 경우에만 `restored`로 쓴다. 현재 값이 이미 원래 값이면 복구된 것으로 보고, 설정 값도 원래 값도 아니면 제3자의 변경으로 보고 덮어쓰지 않는다. 계정 비활성화도 끈 뒤 읽어서 확인한다. 정리는 항목마다 독립 실행해서 하나가 실패해도 나머지를 건너뛰지 않으며, 하나라도 실패하면 종료 코드는 70이다. 프로브 관측 결과(`verdict`)와 정리 결과(`cleanup`)는 보고서에 따로 남는다.

## 6. 한계와 잔여 위험

- 이 묶음의 `-Apply`/`-Execute` 경로는 **실제 Windows에서 한 번도 실행되지 않았다.** 실제 환경에서 확인한 것은 읽기 전용 사전 점검, dry-run, 거부 경로, `-Discover`뿐이다. 적용·검증·복구의 본문은 모의 시스템 위에서만 돌렸다. 모의는 `auditpol`·방화벽·계정·`Start-Process -Credential`·Security 로그를 **우리가 이해한 대로** 흉내 낸 것이라, 이 통과가 실제 동작의 증거는 아니다. 모의 시험이 이미 실제 코드 결함 네 건을 찾았다는 사실(9절)은 실제 환경에서 처음 실행할 때 모의가 흉내 내지 못한 오류가 더 나올 수 있다는 뜻이기도 하다.
- 정리는 읽어서 확인하지만, 읽기 자체가 실패하면 "복구됐는지 모른다"로 남고 사람이 확인해야 한다(`READ_FAILED`, 종료 코드 70/40). Ctrl+C로 중단하면 정리는 하지만 보고서를 못 쓸 수 있다.
- 감사 값이 `DRIFT`로 남는 경우(제3자가 바꾼 값)는 덮어쓰지 않으므로, 그 시점의 감사 값은 원래 값과 다를 수 있다. 종료 코드 70과 보고서의 `cleanup.items`가 그 사실을 알린다.
- 계정 단위 규칙이 **서비스가 대신 수행하는 통신**을 막지 않을 수 있다. 예: 이름 확인은 `Dnscache` 서비스가 질의한다. 이 경우 호스트 이름이 밖으로 새도 TCP 연결은 막힌다(추정, 미관측). 이 묶음은 DNS를 프로브하지 않는다.
- 프로브는 TCP IPv4 두 가지뿐이다. UDP·ICMP·IPv6·DNS와 `semgrep` 자체는 관측하지 않았다. `PROBE_ISOLATION_OBSERVED`를 그쪽으로 넓혀 읽으면 안 된다.
- 가상환경의 `Scripts\python.exe`는 venv 실행기일 가능성이 있고(크기만 확인), 그러면 실제 프로세스의 실행 파일 경로가 기반 `python.exe`로 보인다. 나중의 실제 도구 실행에서 5157의 `Application`과 기록한 경로를 맞출 때 영향을 줄 수 있다(미관측).
- 실패 감사를 켜는 동안 이 PC 다른 프로그램의 차단 연결도 같은 로그에 쌓인다. 이미 가득 찬 순환 로그(3.2절)에서 다른 감사 기록을 더 빨리 밀어낼 수 있다. 창을 검증 실행 동안으로 줄인 이유다.
- 전용 계정은 켜져 있는 동안 로컬 로그온이 가능한 일반 계정이다. 암호는 DPAPI 파일에만 있고 계정은 평소 비활성이지만, 로그온 제한 정책은 걸지 않았다.
- `-GrantReadExecute`는 기존 설치의 ACL을 바꾼다(SID 한 건). 복구는 그 SID의 ACE만 제거한다. 출처 불명의 SID `…-1004` ACE는 건드리지 않는다.
- 백신·EDR, SmartScreen, 그룹 정책이 규칙이나 프로세스 실행에 개입하는지는 모른다(도메인 미가입, Home이라 로컬 그룹 정책 편집기가 없다는 점은 정책 개입 가능성을 줄일 뿐 없애지 않는다).
- 사전 점검 스냅숏(`preflight.json`, 약 0.5MB)은 방화벽 규칙 전체의 이름·상태를 담는다. 저장소 밖(`%LOCALAPPDATA%\bosang-radar\semgrep-isolation\<RunId>`)에만 두고 커밋하지 않았다.
- 복구의 ACL 읽기 실패는 이제 항목별 `FAILED`로 남지만, **진짜 `Get-Acl`의 파일·폴더 접근 거부는 재현하지 못했다.** 모의는 예외나 빈 값을 주입한 것이고, 이 PC의 읽기 관측은 관리자 셸이라 접근 거부가 나오지 않았다(10절).
- 복구 함수에는 **같은 모양이 아니라서 이번에 고치지 않은 지점**이 있다. 코드를 읽고 적은 **가설이며 시험으로 확인하지 않았다.** ① 계정(`Get-LocalUser`)·방화벽 규칙(`Get-NetFirewallRule`)·프로필(`Get-CimInstance`) 조회가 `-ErrorAction SilentlyContinue`라서, 조회 자체가 실패하면 "없음"(`SKIPPED_ABSENT`)으로 기록되고 종료 코드 0이 될 수 있다. ② 실행 기록(`resources.json`) 읽기와 마지막의 복구 기록·실행 기록 쓰기는 `try` 밖이라 실패하면 함수가 예외로 끝난다. 이름으로 찾는 대체 복구는 기록 파일이 "없을 때"만 동작한다.

## 7. 소유자 결정이 필요한 것

1. 전용 계정이 가상환경·기반 Python을 읽도록 **기존 설치의 ACL에 SID 한 건을 추가**해도 되는가, 아니면 접근 가능한 위치에 재설치하는 쪽을 택할 것인가(4.4절).
2. 검증 실행 동안 **감사 정책을 임시로 바꾸는 것**(Filtering Platform Connection 실패)을 허용하는가. 선택으로 "Process Creation" 성공 감사까지 켤 것인가.
3. 프로브 실행 때 **전용 계정의 프로필 폴더가 생기는 것**과, 문서용 예약 주소 `192.0.2.1:9`로 TCP 연결 시도(SYN)가 이 PC 밖 네트워크 장비를 거칠 수 있는 것을 허용하는가.
4. `-IncludeSelfAddressProbe`(방화벽 앱 허용 대화상자가 뜰 수 있음)를 쓸 것인가.
5. 위 허용 뒤 단계 3(적용)과 단계 4(검증 실행)를 진행해도 되는가.

### 수정

- **ACL 단계(`IsolationFlows.ps1`)**: 대상마다 경로 확인 → `Get-Acl`(`-ErrorAction Stop`) → 기록된 SID 대조 → 변경을 한 `try`에 넣고, 예외는 그 대상의 `FAILED`로 기록한다(실패한 단계 이름이 같이 적힌다). `Get-Acl`이 오류 없이 `$null`을 돌려주는 경우도 실패로 본다. 실패한 대상은 `Set-Acl`을 부르지 않으므로 기존 ACL을 덮어쓰지 않고, 다음 대상으로 넘어간다.
- **작업 폴더 단계**: 소유 확인(경로 확인, `.owner` 읽기)과 삭제를 두 개의 `try`로 나눴다. 소유를 확인하지 못하면 `FAILED`로 남기고 지우지 않는다. 삭제 자체의 실패는 기존 처리 그대로다.
- **암호 파일 단계**: 경로 확인(`Test-Path`)을 기존 `try` 안으로 옮겼다.
- 전체를 감싸 예외를 무시하는 방식은 쓰지 않았다. 오류는 항목별 결과로 모이고 종료 코드 40·`recovered-with-issues`에 반영된다. 변이 점검 M7(예외를 기록 없이 삼킴)이 이 차이를 시험이 잡는지 확인했다(아래).

### 실제 Windows(이 PC)에서 읽기 전용으로 관측한 것

진짜 `Get-Acl`이 읽기에 실패할 때의 동작만 관측했다(ACL을 바꾸지 않았다). 이 셸은 관리자 권한이라 `C:\System Volume Information`은 읽혔고, 파일·폴더 ACL의 접근 거부는 재현하지 못했다.

| 대상 | 기본 오류 설정(`Continue`) | `Stop` 또는 `-ErrorAction Stop` |
| --- | --- | --- |
| 없는 경로 | pwsh 7.6.9·5.1 모두 비종료 오류 + `$null` 반환, 예외 없음 | 예외 |
| 접근 불가 레지스트리 키 `HKLM:\SAM\SAM` | pwsh 7.6.9는 **오류 없이 `$null`**, 5.1은 "경로를 찾을 수 없다" 오류 | pwsh는 `$null` 그대로(예외 없음), 5.1은 예외 |

호출자의 오류 설정에 따라 예외가 되기도 하고 `$null`이 되기도 하며, 오류 없이 `$null`이 돌아오는 경우가 실제로 있었다(레지스트리 키, pwsh). 그래서 수정은 `-ErrorAction Stop`을 명시하고 `$null`도 실패로 본다. 진입 스크립트는 `$ErrorActionPreference = 'Stop'`이라, 비종료 오류를 내는 읽기 실패는 운영 경로에서 예외가 된다(지적된 흐름과 같다). 파일·폴더 ACL의 접근 거부가 어느 쪽으로 나오는지는 관측하지 못했다.

시험 뒤 이 PC에서 읽기 전용으로 다시 확인했다(전후 비교가 아니라 사후 확인): `bsi*` 로컬 계정 0개, `bosang-semgrep-iso` 방화벽 규칙 0개, `%ProgramData%\bosang-semgrep-iso` 없음, 임시 샌드박스 0개, Filtering Platform Connection 감사 `No Auditing`.

### 이번에 새로 확인된 것과 확인되지 않은 것

- 합성에서 확인: 복구의 ACL·작업 폴더·암호 파일 단계가 읽기·확인 실패 한 건에 멈추지 않고, 실패 항목은 `FAILED`로 남아 건드려지지 않으며, 종료 코드 40·`recovered-with-issues`와 완료·실패 항목 기록이 남는다. 정상 복구·dry-run·소유 불일치 거절은 그대로다.
- 실제 Windows에서 확인: 위 `Get-Acl` 읽기 실패 동작의 읽기 전용 관측뿐이다.
- **확인하지 못한 것:** 진짜 파일·폴더 ACL의 접근 거부에서의 `Get-Acl` 동작, 6절의 두 가설, 실제 계정 생성·규칙·감사 변경·ACL·전용 계정 프로브 실행과 그 효과. 모의 시험의 통과는 실제 동작의 증거가 아니다.
