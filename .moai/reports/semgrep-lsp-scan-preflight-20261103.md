## 2. 동작

### 2.1 확인 인자 (F5-1)

- 이름은 `-ConfirmRunId`다. 값은 이번 실행 기록(`resources.json`)의 RunId와 **서수 비교**로 정확히 같아야 한다. 대소문자만 다른 값, 앞뒤 공백, 접두만 같은 값, 소프트 하이픈(U+00AD)이나 NUL이 낀 값은 모두 다른 값이다. PowerShell의 `-ceq`는 서수 비교가 아니라 문화권 비교라서 소프트 하이픈·NUL이 낀 값을 같다고 보므로 `[string]::Equals(…, Ordinal)`을 쓴다. 단위 시험이 이 차이를 직접 대조하고, 변이로 `-ceq`를 넣으면 실패한다.
- 적용 범위는 `-Mode semgrep-lsp`와 `-Execute`가 **함께** 있을 때뿐이다. 스텁 모드와 dry-run은 달라지지 않는다. 확인 인자만 줬다고 실행하지 않는다(dry-run은 맞는 인자를 줘도 `NOT_EXECUTED`, 표지 없음).
- 시점: RunId 형식 검사 바로 뒤, 사전 조건 읽기보다 앞이다. 없거나 다르면 종료 30으로 거부하며, 계정 켜기·감사 변경·수신기 생성·작업 배치 변경·러너 실행은 모두 0건이다(모의 `calls.log`로 센다). 거부 메시지에는 기대 RunId를 적지 않는다.
- 사용 예와 문구는 `windows/README.md`와 진입점 머리말에 있다.

### 2.2 실행 시도 표지 (F5-2)

- 경로: `<RunDir>\lsp-scan-attempt.marker`(실행 기록 폴더 바로 아래, 기존 증거 파일과 같은 곳).
- 확보 시점: 모든 읽기 전용 사전 조건과 확인 인자를 통과하고 dry-run 반환을 지난 뒤, 첫 실행 부작용(수신기·감사 창·계정 켜기·작업 배치 삭제와 복사) 앞이다. 소스상 순서와 모의 호출 로그의 순서를 둘 다 시험이 고정한다.
- 생성: `FileMode.CreateNew` 배타 생성이다. 여덟 실행 공간을 한 문에서 동시에 출발시킨 시험에서 정확히 하나만 성공하고 일곱이 거절됐으며, 본문은 이긴 호출의 것 하나뿐이었다.
- 거절(새 표지를 만들지 않음): 표지가 이미 있다(종료 30), 같은 실행 기록 폴더에 SCAN 산출물이 이미 있다(종료 30), 산출물 목록을 읽지 못했거나 표지를 만들지 못했다(종료 50).
- "기존 SCAN 관측 기록"의 정의: 실행 기록 폴더 바로 아래의 `lsp-scan-observation-`, `-record-`, `-runner-result-`, `-admin-context-`, `-stdout-`, `-stderr-` 접두 파일이다. 이 진입점이 한 번의 실행에서 남기는 산출물 전부이므로, 관측 보고서만 지워도 나머지가 남아 재사용을 막는다. 과거 MIN(`lsp-min-…`)·RULES(`lsp-rules-…`) 기록과 취소 표지(`lsp-scan-cancel.flag`)는 세지 않는다(단위·흐름 시험이 확인). 스텁 모드 실행의 산출물도 같은 접두를 쓰므로, 스텁을 돌린 실행 기록 폴더로는 실제 모드를 거절하게 된다(코드상의 결과이며 이 조합을 따로 시험하지는 않았다). 스텁은 별도 RunId로 돌려야 한다.
- 수명: 표지를 확보한 뒤 실패·취소·중단되어도 자동 삭제하거나 재시도 가능 상태로 돌리지 않는다. 새 시도에는 새 RunId가 필요하다. `-Force`, 덮어쓰기, 표지 복구·삭제 기능은 없다. 정적 시험이 (a) 진입점 매개변수에 그런 이름이 없고 (b) 표지 포트에 `CreateNew` 외의 파일 모드·삭제·이름 바꾸기가 없고 (c) 표지를 지우는 코드가 없음을 고정한다.
- 경로 보호: 표지는 실행 기록 폴더 아래에만 만든다. 만들기 전에 실행 기록 폴더(신뢰 루트)부터 표지 자리까지 경로 조각에 링크가 없는지 기존 확인 함수(`Get-LspMinWorkPathProblems`)로 본다. 표지 자리에 (바깥을 가리키는) 정션이 이미 있거나 실행 기록 폴더 자체가 정션이면 따라가지 않고 거절하며, 가리키는 바깥에 아무것도 만들지 않았다(시험).
- 복구와의 관계: `Remove-Isolation.ps1`·`Initialize-Isolation.ps1`은 표지를 읽지도 확인하지도 않는다(정적 시험). 표지가 있는 상태에서 복구 스크립트가 정상 종료(0)하고 표지를 지우지 않음을 흐름 시험이 확인한다. 표지를 확보한 뒤 실패해도 이 진입점의 정리(`finally`: 프로세스 정리, 계정 비활성화, 감사 값 복구)는 그대로 끝까지 돈다.
- 기록의 구분: 보고서의 `attemptMarker`(`applicable`, `path`, `createdUtc`, `acquired`, `autoDelete=false`, `retryable=false`)는 `processCleanup`·`systemRecovery`와 별도 필드이며 서로의 결과를 바꾸지 않는다. 스텁 모드는 `applicable=false`다.
- 범위: 범용 잠금·복구 프레임워크로 넓히지 않았다. 새 코드는 계약 함수 4개, 포트 함수 2개, 진입점의 한 블록이 전부다.

### 2.3 mode 교차 확인 (F6a)

- TS(`reinterpretScanRun`): 관리자 문맥의 `mode`와 러너 결과의 `mode`가 모두 `stub` 또는 `semgrep-lsp`이고 같을 때만 러너 결과의 출처를 쓴다. 그렇지 않으면 출처를 `null`로 비우고 사유를 남겨 관측이 성립하지 않는다.
  - 관리자 mode 없음·모르는 값: `ADMIN_CONTEXT_MALFORMED:mode`
  - 러너 mode 없음·모르는 값: `ADMIN_RUNNER_MODE_INVALID`
  - 서로 다름: `ADMIN_MODE_MISMATCH:admin_stub_runner_real`(러너의 자기 보고만으로 올리려는 경우), `ADMIN_MODE_MISMATCH:admin_real_runner_stub`
- 출처가 `null`이면 기록은 `SYNTHETIC_STUB_ONLY`이고 `established`가 비며 `real_binary_verified`는 거짓이다. 관리자 mode만 보고 출처를 채우거나(변이 T6) 러너 자기 보고만으로 올리는 것(변이 T5)을 시험이 막는다. 송신 기록과 원문 증거(`both_complete_at_ms` 등)는 지우지 않는다.
- 러너를 띄우지 않았다고 알린 경우(`runnerLaunched=false`)에는 러너 결과가 남아 있어도 그 mode로 출처를 정하지 않으며(출처 `null`), 관리자 mode가 틀렸으면 문맥 문제로 남는다.
- PowerShell(`Test-LsAdminResultBinding`): 기존 검사(`Test-LspMinResultBinding`의 `MODE_MISMATCH`)를 유지하고, 결과 mode가 `stub`·`semgrep-lsp`가 아니면 `MODE_INVALID`, 요청 mode와 서수로 다르면 `MODE_MISMATCH`를 더한다. 기존 비교(`-cne`)는 소프트 하이픈·NUL이 낀 값을 같다고 볼 수 있어서다. 공용 MIN 파일은 바꾸지 않았다.
- 시험 보조 `adminContextFor`는 문맥에 `mode`를 기본으로 싣는다(사실의 출처와 같은 쪽). 이 보조는 이 PR이 더한 파일이다.

### 4.1 수정 전 실패

- TS: `reinterpretScanRun`에 mode 확인이 없던 상태에서 새 시험 7건 중 6건이 실패했다(양방향 불일치, 관리자 mode 없음·모르는 값, 러너 mode 없음·모르는 값, 미실행 경로 두 건). 정상 두 종류를 확인하는 1건은 원래 맞던 경로의 대조군이라 통과했다.
- PowerShell F5는 새 기능이라 "수정 전 실패" 대신 아래 변이로 확인했다. 흐름 시험은 첫 실행에서 모두 통과했으므로, 시험이 헛통과가 아님을 변이로 증명했다.
- 시험을 쓰는 과정에서 시험 쪽 결함 세 가지를 시험이 먼저 드러냈다: `@()`로 한 번 더 감싼 `, @(…)` 반환값(포트의 경로 문제 판정이 항상 "문제 있음"으로 읽혀 표지를 못 만들었다 — 단위 시험이 잡고 고쳤다), `CreateNew`를 `Create`로 오인한 정적 정규식, 5.1이 빈 문자열 인자를 자식에게 넘기지 않는 문제(흐름에서 빼고 단위로 옮겼다).

| P5 | `CreateNew` → `Create`(덮어쓰기) | 정적 1 + 단위 2(동시 시도에서 4승 4패) |
| P6 | 표지 경로 링크 확인 | 단위 2건(링크 자리·링크 폴더) |
| P7a | SCAN `stdout` 접두 | 단위 2건 |
| P7b | MIN 기록을 SCAN 으로 셈 | 단위 3건 |
| P8a | 결합의 `MODE_INVALID` | 단위 8건 |
| P8b | 결합의 서수 `MODE_MISMATCH` | 단위 2건 |
| P9 | 기존 SCAN 산출물 조회 | 단위 1건 |
| E1 | 확인 인자 거부 | 흐름 `confirm` 다수(러너 직전 MOCK GUARD까지 진행) |
| E2 | 기존 산출물 거절 | 흐름 `marker` 3건 |
| E3 | 표지 존재 무시 | 흐름 `marker` 2건 |
| E4 | 정리에서 표지 삭제 | 흐름 `marker-run` 다수 |
| E6 | 스텁 모드에도 확인 인자 요구 | 흐름 `control` 8건 |

변이로 확인하지 못한 것: 표지 확보를 첫 부작용 뒤로 옮기는 변이(순서는 정적 소스 순서 시험과 호출 로그 순서 시험 두 곳이 고정하지만, 이 둘의 민감도를 변이로 따로 확인하지는 않았다), 보고서 `attemptMarker` 필드별 값, 동시 생성의 흐름 수준(진입점 두 개 동시 실행) 변이.

## 6. 남은 한계

1. 실제 Semgrep, 전용 계정, 방화벽, 감사, ACL 아래의 동작은 한 번도 관측하지 않았다. 시험의 `semgrep-lsp` 분기는 설치물 확인이 모의다(진짜 `Test-LsAdminInstall`은 모의 없는 사례에서 가짜 경로를 보고 사전 조건 실패로 닫히는 것까지만 확인했다).
2. 5.1 호스트에서만 돌렸다. Linux PowerShell과 다른 Windows 버전은 미검증이다.
3. 산출물 조회와 표지 생성 사이에 시간차가 있다. 다른 호출이 그 사이에 끝까지 마치는 경우는 표지(또는 산출물)가 남아 있어 한쪽에서 거절되지만, 이 경계를 실제 시스템에서 관측하지는 않았다. 표지 생성 직후 프로세스가 강제 종료되면 표지(빈 파일일 수 있음)만 남아 RunId가 소모되는 쪽으로 기운다.
4. 경로 조각 링크 확인은 실행 기록 폴더(신뢰 루트)부터 표지까지만 본다. 상태 루트 등 상위 경로와 하드 링크는 보지 않으며(기존 증거 쓰기와 같다), 확인 뒤 링크로 바뀌는 경쟁 상태는 막지 못한다.
5. 표지는 실행 기록 폴더 단위다. 다른 RunId(다른 폴더)로 새로 격리를 적용해 실행하는 것을 막지 않는다 — 그것은 승인 절차(D2)와 새 격리 기준의 몫이다. 확인 인자는 오타·복사 실수를 줄일 뿐 의도적인 우회를 막지 않는다.
6. 이 PR이 PR #43 위에 쌓이므로, PR #43의 F3(마감 뒤 settle 진입 차이), 로그 분석 성능, JSON 해석기 차이는 그대로 남아 있다(이번 범위 밖으로 유지).
7. 스텁 모드로 쓴 실행 기록 폴더는 실제 모드를 거절한다(같은 접두의 산출물이 남기 때문). 의도한 보수적 선택이지만 시험으로 확인하지는 않았다. 스텁 점검은 별도 RunId로 해야 한다.

## 7. 이번 작업이 하지 않은 것

Semgrep의 실행·임포트, 계정·방화벽·감사·ACL 적용, 네트워크 프로브, 규칙 다운로드, 실제 대상 스캔, 기존 관측의 재실행, D2 승인, `pin.json`·`verified`·`policy_accepted`·ADR 상태 변경, 기존 PR(#43 포함)·`main`·보담 저장소 변경, 병합·배포, 독립 감사, 대규모 변이 점검, 프레임 파서·TS 스캔 계약·골든 변경.
