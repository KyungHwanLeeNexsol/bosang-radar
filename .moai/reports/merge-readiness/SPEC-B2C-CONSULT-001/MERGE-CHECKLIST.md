## 1. 병합이 자동으로 실행하는 것 (`.github/workflows/deploy.yml`)

**`main`에 푸시되는 순간 배포가 시작된다**(트리거는 `push: main`과 수동 실행 `workflow_dispatch`뿐). 병합은 곧 배포다. 스크립트는 `set -euo pipefail`이라 한 단계라도 실패하면 거기서 멈춘다.

| 순서 | 단계 | 실패하면 |
|---|---|---|
| 1 | `git fetch` → `git reset --hard origin/main` → `pnpm install --frozen-lockfile` | 중단. 옛 빌드가 계속 가동 |
| 2 | **`pnpm run db:migrate`** (이 PR은 `0009`: 테이블 2개 + 유니크 인덱스 3개 추가) | 중단. 빌드·재시작 안 함 |

| 4 | PM2 앱 존재 확인 → **`pm2 restart`** → `pm2 save` | 새 빌드가 곧바로 서비스에 올라감 |
| 5 | smoke check 3종: `GET /`가 2xx, 본문에 "서비스 준비 중입니다", CSS 청크가 2xx | **재시작 뒤라서 실패해도 새 빌드는 이미 가동 중**(Actions만 빨강) |

## 3. 마이그레이션 직전 백업과 실패 대응

### 3.1 무엇이 적용되나

`db/migrations/0009_abnormal_owl.sql`은 `consultation_rate_limits`, `consultations` 테이블과 유니크 인덱스 3개를 **만들기만 한다**(파일을 읽음). 기존 테이블은 바꾸지 않는다. 마이그레이션은 Drizzle `migrate`가 `@libsql/client`의 `migrate`를 거쳐 한 배치로 실행하는데, 라이브러리 코드(`executeHranaBatch`)상 `BEGIN → 문장들 → COMMIT`이고 실패하면 `ROLLBACK`한다. **운영에서 실패를 일부러 일으켜 본 적은 없다.**

### 3.2 대상 DB

운영 VM 앱 폴더의 `.env` 두 곳이 정의한 `TURSO_DATABASE_URL`의 지문(`sha256(URL.trim())` 앞 8자리, 하네스와 같은 계산)이 모두 **`6e5256b8`**이다. 원격 T1~T7과 백업을 한 대상의 지문도 `6e5256b8`이다. 즉 지문 기준으로 **원격 시험은 운영 VM이 설정한 DB에서 수행됐다.** 실행 중 앱이 이 `.env`를 읽는지는 프로세스 환경에 이 변수가 없다는 점에서 추정한 것이며 직접 확인하지 않았다.

그 시험은 `0009` 적용 → 가상 데이터 → 정리 → `0009` 되돌림까지 했고, 되돌린 뒤 스냅샷이 마이그레이션 직전 백업과 13개 테이블·스키마가 일치했다(런북 §12.9). 따라서 병합 때 `0009`가 새로 적용될 것으로 예상하지만 **오늘 DB 상태는 읽지 않았다.**

### 3.3 병합 직전 백업 (사용자 승인·실행 필요, 미수행)

1. DB 상태 읽기 전용 확인: `0009` 두 테이블이 **없고** `__drizzle_migrations`가 **9행**인지.
2. 읽기 전용 단일 스냅샷 백업 → 로컬 임시 DB로 복원 리허설 → 테이블별 행 수·내용 SHA-256·스키마 SHA-256 비교(런북 §12.8 2단계).
3. 이 PC의 gitignored 일회용 스크립트 `.tmp/turso-backup.mjs`, `turso-restore-rehearsal.mjs`, `turso-discover.mjs`를 쓴다(저장소에 없다). **실행 전에 스크립트가 접속 정보를 어디서 읽는지 읽어서 확인한다.** 백업 파일은 저장소 밖에 두고 값·URL은 문서·로그에 적지 않는다.
4. 직전 기준선(2026-09-30 백업, 스키마 해시 `d8a6a12d87bb`, `__drizzle_migrations` 9행)과 비교해 그 사이 변동이 없는지 본다.
