## 2. 계약 정정: 수신 순서 (PR #42의 C12와 관련 시험 계획)

### 2.1 무엇이 잘못이었는가

계획의 C12는 "`didOpen` 송신 → `Scanning single file` → `Scanning 1 targets` → … → 알림" 순서와 "알림은 `didOpen`으로부터 `scanMs` 안에 도착"을 함께 요구했다. 앞의 순서는 stdout 프레임과 stderr 로그 줄의 **수신 순서**에서 서버 내부 실행 순서를 읽어 내는 것이다. 두 스트림은 서로 다른 파이프라 버퍼링과 읽기 주기가 독립이므로, 한쪽 청크가 먼저 읽혔다는 사실은 서버가 그쪽을 먼저 썼다는 뜻이 아니다. 근거가 없는 단정이므로 계약에서 뺀다.

### 2.2 정정한 규칙

1. 판정과 중단 결정은 stdout과 stderr 사이의 수신 순서·수신 시각 차이에 의존하지 않는다. 진단 알림이 먼저 읽히든 엔진 로그가 먼저 읽히든, 청크가 어떻게 쪼개지든, 동시에 도착하든, 증거가 완전하고 서로 일치하면 같은 성공 판정이다.
2. 순서는 **각 스트림 안에서만** 본다. stdout은 바이트·프레임 경계와 프레임 순서, stderr는 필수 로그 묶음의 줄 순서다. `Scanned single file`은 비동기 작업을 만든 시점에 찍히므로(계획 P37) 순서 기준도 완료 신호도 아니며, `Scanning single file` 뒤 어디에 나와도 된다.
3. `didOpen` 송신 시점에 각 스트림에서 이미 읽은 바이트 수를 기록하고, 그 위치로 사전/사후 구간을 가른다. 줄·프레임의 **첫 바이트**가 소속을 정한다. 사전 구간에 있는 진단 프레임이나 스캔 증거 모양의 로그 줄은 이번 스캔의 증거로 세지 않으며, 그런 줄이 있으면 `NOT_CONFIRMED:PRE_OPEN_EVIDENCE`로 닫는다(허용되는 사전 구간 줄은 규칙 로딩 장벽의 줄, 장벽 단계의 `No targets to scan!` 경고 1건, 외부 명령 시도 1건뿐이다).
4. `didOpen` 뒤에는 **두 증거 묶음이 모두 완성되고 서로 일치해야** 한다. 진단 묶음은 유효한 알림 정확히 1건(진단 1개)이 끝까지 수신된 것이고, 엔진 로그 묶음은 필수 줄이 모두 줄바꿈까지 수신돼 스트림 안의 정해진 순서를 지킨 것이다. 알림만 있거나 로그만 있으면 성공이 아니다. 둘 다 `didOpen`으로부터 `scanMs`(30000) 안에 완성돼야 한다.
5. `settleMs`(2000)는 두 묶음이 모두 완성된 시점, 곧 **늦게 완성된 묶음의 마지막 청크 시각**부터 센다. 먼저 도착한 증거의 시각으로 거슬러 세지 않는다. 이 창에서 추가 진단 알림, 추가 스캔 줄, 금지 신호, 서버 요청이 하나라도 있거나 프로세스가 끝나면 성공이 아니다.
6. 로그의 `Found 1 matches`가 알림의 진단 수와 같고, `Scanned 1 files`가 알림의 URI 수와 같으며, 알림의 파일이 대상 파일이어야 한다(계획 C10 유지).

### 2.3 줄이지 않은 것, 보존한 것

필요한 증거(진단 1건 + 완전한 로그 묶음), 개수(`didOpen` 1회, `initialized` 1회, 외부 명령 시도 사전 1·사후 1), 필드(URI·`code`·`source`·`message`·`severity`·범위), 한도(`scanMs`, `settleMs`, 기존 전체·초기화·종료 한도)는 모두 그대로다. 한도는 낮출 수만 있고 늘리거나 자동으로 연장하지 않으며 재시도도 없다. PR #42의 보고서와 LSP-RULES-1의 원본 증거는 수정하지 않았고, 이 절이 정정한 조건과 이유를 적는다.

### 2.4 실행 수준의 동작과 독립 검토 후의 정정

마감(`didOpen + scanMs`)까지 두 묶음이 완성되지 않으면 실행기는 기다림을 끝내고 정상 종료 절차(`shutdown` → `exit`)로 간다(트리거 `SCAN_TIMEOUT`). 마감 뒤에 도착한 증거는 원문에 남고 판정이 늦은 증거로 가른다.

- 아무것도 오지 않았다: `NOT_CONFIRMED:SCAN_TIMEOUT`
- 한쪽 묶음만 왔다: `NOT_CONFIRMED:NO_DIAGNOSTIC_NOTIFICATION` 또는 `NOT_CONFIRMED:ENGINE_LOG_MISSING`
- 한 묶음이 마감 뒤에 완성됐다: `NOT_CONFIRMED:EVIDENCE_AFTER_DEADLINE`

세 번째가 처음 구현에서는 `NOT_OBSERVED:SETTLE_WATCH_NOT_CONFIRMED` 뒤에 가려졌다(독립 검토 F1). 마감에서 기다림을 끝내므로 settle 감시를 마쳤다는 증거가 원래 없는데, 늦은 묶음 때문에 `bothCompleteAtMs`가 채워져 감시 미확인이 판정 자리를 차지한 것이다. 늦은 경우에 한해 감시 미확인이 판정 자리를 양보하도록 고쳤다(조건 13에는 사실대로 남는다). 이 정정으로 성공이 될 수 있는 경로는 늘지 않았다. 늦은 묶음은 어느 쪽이든 성공이 아니다. 같은 이유로 늦은 경우의 `EXIT_DURING_SETTLE`은 우리가 `shutdown`을 보내기 **전에** 프로세스가 끝난 경우에만 사유로 남긴다. 그 이전의 종료와 종료 시각을 모르는 경우는 늦음과 무관하게 그대로 `NOT_OBSERVED`다.

## 7. 남은 한계

1. **실제 Semgrep 바이너리에서의 동작은 한 번도 관측하지 않았다.** 로그 문구, 필수 줄 순서, 진단의 `uri` 인코딩, `code` 접두, 범위의 끝 열 기준, 진단 객체의 추가 필드는 공개 소스 읽기에서 도출한 값이며 바이너리와의 대응은 증명되지 않았다(계획 8절의 한계 그대로). 맞지 않으면 실제 실행은 `NOT_CONFIRMED` 계열로 닫히도록 설계했고, 실제 출력을 본 뒤 허용 규칙을 넓히지 않는다.
2. 이 PC의 5.1에서만 시험했다. 다른 Windows 버전, pwsh 7, 다른 PC는 미검증이다.
3. 시스템 격리(계정·방화벽·감사·ACL·5157 대조)는 모의로만 확인했다. 기존 격리·정리·복구 절차는 재사용했고 바꾸지 않았다.
4. `Test-LsAdminInstall`(설치물 확인 L01-L11)과 `semgrep-lsp` 모드 전체는 모의가 막아 시험하지 못했다.
5. PowerShell 러너는 읽기 반복의 시작 시각을 청크 도착 시각으로 쓴다. 그 반복 한 번의 길이가 0.5초 안팎까지 갈 수 있다는 정황이 있으나(스텁 간격 500ms에서 같은 시각으로 찍힌 실행이 있었다) 원인과 크기는 확인하지 않았다. 정시 도착 증거가 마감 직전에 도착하면 늦게 찍혀 `late`로 기울 수 있고, 이 방향은 성공이 아닌 쪽이다.
6. 실제 크기의 stderr에서의 PowerShell 로그 분석 지연은 재지 않았다.
7. 마감 경계(정확히 `scanMs`에 완성되는 묶음)와 `didOpen` 오프셋에 걸친 프레임·줄은 TS 시험에는 있으나 PowerShell 쪽 골든에는 없다.
8. 엔진이 프로세스 안에서 도는 동안의 동작은 프로세스 트리로 보이지 않고 로그 줄에 의존한다. `git` 프로세스의 생성 여부는 D3 (a)를 고른 이상 관측되지 않는다(시도 로그와 별개 사실로 기록하며 "없었다"고 쓰지 않는다).
9. 이 PR의 판정은 합성 입력 한 건의 양성 반응 한 번을 보려는 것이다. 실제 저장소 스캔, 보안 게이트, 음성 대조, 대조 참조 자격으로 연결하지 않으며 어디에도 연결하지 않았다.

## 9. 서식 검사에 대한 기록

- 저장소의 `format:check`(`prettier --check .`)는 `.prettierignore`의 `.moai` 때문에 `.moai/reports/*.md`를 검사하지 않는다. **이 보고서는 그 검사의 대상이 아니므로 서식 검사를 통과했다고 쓰지 않는다.** prettier의 서식 규칙(열 정렬 등)은 이 보고서에 적용하지 않았다.
