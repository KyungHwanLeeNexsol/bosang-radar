# SPEC-PILOT-UX-001 — Implementation Plan

## §A. Key Decisions (highest change-likelihood — read this first)

Per decision-reversibility ordering, these are the decisions most likely to need revision during review or implementation. Everything else in this plan is a comparatively mechanical consequence of these decisions.

1. **Client-only single-flight submission guard** (`case-input-form.tsx` + `feedback-form.tsx` — the sole mechanism-level decision in this SPEC, replacing the originally-planned DB-backed idempotency from iteration 2). Both forms gain a `useRef<boolean>(false)` guard set to `true` synchronously at the start of the submit handler, checked BEFORE any `fetch`/`action` call — When the guard is already `true`, the handler returns immediately without issuing a second request. This is a pure client-side single-flight guard, NOT idempotency: it prevents a double-click or rapid re-invocation from firing two requests from the SAME mounted form instance; it does NOT protect against two separate browser tabs, a page reload mid-request, or a server crash between request receipt and response. **Rejected alternative (formerly the accepted design in iteration 2)**: server-side idempotency via a nullable `submissionNonce` column + unique index on `cases`/`feedback`, with the server skipping `runPipeline`/insert on a repeated nonce. This was rejected in iteration 3 following an external independent review: `createCase`'s actual execution order is `validate → runPipeline → cases insert → reports insert`, so a SELECT-before-`runPipeline` + unique-index-after-`runPipeline` check does NOT prevent two concurrent requests carrying the same nonce from BOTH running the (expensive) Gemini pipeline — the race window is exactly the pipeline's own execution time. Correctly solving this requires a genuinely different design (e.g., a reserved/pending row inserted BEFORE the pipeline runs, with crash-recovery semantics for abandoned reservations); this is out of scope for a private-pilot UX SPEC and is deferred to a future SPEC candidate (see Out of Scope — 분산 서버측(DB 기반) idempotency in spec.md).
2. **Report summary-banner data shape** (`page.tsx`) — the aggregate verdict banner (REQ-PILOT-UX-004) is computed inline from the already-fetched `report.verifiedClaims` array (a `reduce`/`filter` count of `VERIFIED` vs non-`VERIFIED`), NOT a new server-side aggregation function or a new field on `ResearchReport`. This keeps `SPEC-RESEARCH-001`'s `ResearchReport` type contract completely untouched (per Out of Scope — AI 파이프라인 알고리즘 변경).

Everything below (UI markup restructuring, SELECT projection expansion, form-state additions) is a mechanical consequence of these two decisions and is unlikely to need independent re-review once §A is approved.

### M2 — Feedback form usability

- Edit `feedback-form.tsx`: add `const submitGuardRef = useRef(false);` and a `submissionSucceeded: boolean` state. At the start of `handleSubmit`, `if (submitGuardRef.current) return;` then `submitGuardRef.current = true;` BEFORE calling `action` (REQ-PILOT-UX-007, §A decision 1). Wrap the `action` call in a `try/catch` (currently a bare `try/finally` with no `catch` — REQ-PILOT-UX-011's action-rejection branch requires one). Three outcomes, each ending the pending state (`setIsSubmitting(false)`):
  - `result.success === false` (validation failure): `submitGuardRef.current = false`, render the per-field `fieldErrors` (next bullet) — the guard reset allows the user to correct the input and resubmit (REQ-PILOT-UX-010).
  - `action` throws or its returned promise rejects (network/server-level failure, caught in the new `catch` block): `submitGuardRef.current = false`, display a human-readable form-level error (reuse the existing `formError`-style pattern from `case-input-form.tsx`) — no unhandled promise rejection (REQ-PILOT-UX-011).
  - success: do NOT reset the guard; set `submissionSucceeded(true)` and render a visible confirmation element (REQ-PILOT-UX-008/009) — a simple `<p>` styled in a success token (e.g. reuse the `bg-secondary`/`text-secondary-foreground` tokens already used by the `claim-status` VERIFIED pill for visual consistency, per Out of Scope — 디자인 시스템 재작성) — and keep the submit button `disabled` when `submissionSucceeded` is `true` (in addition to the existing `isSubmitting` check). A fresh page load or re-navigation creates a new component instance with a fresh `useRef`, so a new logical submission is naturally allowed there — no explicit reset needed for that case.
  This is the direct feedback-form counterpart of `case-input-form.tsx`'s guard-reset-on-failure / persist-on-success pattern (§B M3 (c)) — the bug this closes: without an explicit failure-branch reset, the guard set `true` at the top of `handleSubmit` would stay `true` forever after the FIRST validation failure, permanently blocking resubmission on that mounted instance even after the user corrects their input.
- Edit `feedback-form.tsx`: for the `result.success === false` branch above, replace the flattened `Object.values(result.fieldErrors).flat().join(" ")` (`:111`) with per-field rendering, reusing the `fieldErrors.x?.map((message) => <p key={message} className="text-sm text-destructive">{message}</p>)` pattern already established in `case-input-form.tsx:73-77` — apply it per the top-level key as `submit-feedback.ts`'s `toFieldErrors` actually produces them (`overallRating`/`overallComment`/`missedIssues`/`claimAssessments`/`evidenceAssessments`/`outcome`/`_form` — top-level only, NOT nested Zod issue paths, since `toFieldErrors` uses `issue.path[0]`), rendered under each corresponding logical section (REQ-PILOT-UX-010).
- Edit `feedback-form.tsx`: wrap the five existing content blocks (overall rating+comment, missed issues, claim verdicts, evidence verdicts, outcome) each in a visually distinct section — a `<div className="flex flex-col gap-2 border-t pt-4">` (or a `Card`/`CardContent` per-section) with a section-title `<p>` — REQ-PILOT-UX-012. This is a pure markup/CSS restructuring; no new client state beyond the guard/success state added above.

## §C. Technical Approach Summary

- **Client-only single-flight guard, no server changes**: both duplicate-submission guards (M2, M3) are a `useRef<boolean>` checked-and-set synchronously at the start of the submit handler, entirely inside the two React client components — no new DB column, no new Zod schema field, and no change to any server write-path (`createCase`, `submitReportFeedback`). This directly matches the external review's finding that this SPEC's scope is UI-layer usability, not distributed-systems correctness.
- **UI-first, zero-schema-impact**: ALL SIX requirement groups (A-F) are pure UI/markup/query-projection changes with ZERO schema or migration impact — this SPEC produces no `pnpm db:generate` output at all.
- **`evidence` SELECT projection expansion is the only query-shape change**: `evidenceType`/`issueTypes` already exist as columns on the `evidence` table (added by SPEC-EVIDENCE-001); this SPEC only widens the existing Drizzle SELECT projection (M1) to include them — an application-level query change, not a schema change.

## §D. Risks

1. **`EvidenceDisplay` interface duplication** (`page.tsx` and `feedback-form.tsx` each define their own local `EvidenceDisplay` interface) — REQ-PILOT-UX-005 requires both to gain the same two fields. Risk: updating one and forgetting the other produces an inconsistent evidence display between the two screens. Mitigation: since both files already duplicate this interface (pre-existing pattern, not introduced by this SPEC), M1 explicitly calls out editing both; self-review before completion should grep both files for `EvidenceDisplay` to confirm parity. Extracting a shared type into `lib/pipeline/types.ts` or a new shared module is a reasonable follow-up but is NOT required by this SPEC (scope discipline — the existing duplication pattern is preserved, not refactored away).
2. **Client-only guard is a known scope limitation, not a defect** — the `useRef` single-flight guard (§A decision 1) protects only against repeated invocation from the SAME mounted component instance. It does NOT protect against: two separate browser tabs/windows submitting concurrently, a page reload mid-request, or a server crash between request receipt and response. This is an explicit, user-confirmed scope narrowing (see Out of Scope — 분산 서버측(DB 기반) idempotency in spec.md) — NOT a bug to fix within this SPEC. Any future report of a duplicate submission caused by one of these excluded scenarios should be routed to a new SPEC for genuine distributed idempotency, not treated as a regression of this SPEC's acceptance criteria.
