# SPEC-PILOT-UX-001 — Implementation Plan

## §A. Key Decisions (highest change-likelihood — read this first)

Per decision-reversibility ordering, these are the decisions most likely to need revision during review or implementation. Everything else in this plan is a comparatively mechanical consequence of these three.

1. **Idempotency mechanism** (`lib/db/schema.ts` — the ONE architecturally significant decision in this SPEC). Both `cases` and `feedback` gain a nullable `submissionNonce: text("submission_nonce")` column with a unique index scoped appropriately (`cases`: unique on `submissionNonce` alone; `feedback`: unique on `(reportId, userId, submissionNonce)` composite, NOT on `(reportId, userId)` alone — the latter would silently reintroduce the uniqueness constraint SPEC-FEEDBACK-001 explicitly rejected). Rejected alternative: a time-window duplicate-detection heuristic (match `input`/`payload` JSON + a short creation-time window, no schema change) was considered and rejected — it is fragile (exact-JSON-match dependent, clock-skew sensitive) and the schema addition is genuinely additive/nullable/backward-compatible, which the SPEC's own constraints explicitly permit ("minimal, additive, backward-compatible" schema changes are pre-authorized). **Resolved (NULL-handling — formerly an open clarification question, resolved in the iteration-2 fix-up)**: per SQLite's official documentation, "For the purposes of UNIQUE constraints, NULL values are considered distinct from all other values, including other NULLs" (sqlite.org/lang_createtable.html, verified via WebFetch). This project's `drizzle.config.ts` declares `dialect: "turso"` — Turso/libSQL is a SQLite-compatible fork and inherits this exact NULL-handling semantics. Consequently, a plain Drizzle Kit `uniqueIndex()` on the nullable `submissionNonce` column is sufficient: any number of rows carrying `NULL` (legacy pre-existing rows, or any future non-idempotent caller) never collide with each other or with a non-NULL value, so **no partial index (`WHERE submission_nonce IS NOT NULL`) is required** — a plain unique index over the nullable column is the final design. M1 still runs the empirical confirmation (read the generated migration SQL + a fixture test inserting two `NULL`-nonce rows, per M1/M6 below) as a mechanical sanity check, not because the semantics are in doubt.
2. **Idempotent response shape on retry** — when a duplicate-nonce request is detected, the write-path returns the SAME success shape as the original request (`{ success: true, caseId }` / `{ success: true, feedbackId, caseId }`), not an error. This treats a nonce collision as "already done, here's the result" rather than "rejected duplicate" — the correct semantics for a client-side retry (network flake, double-click), distinct from a validation failure.
3. **Report summary-banner data shape** (`page.tsx`) — the aggregate verdict banner (REQ-PILOT-UX-005) is computed inline from the already-fetched `report.verifiedClaims` array (a `reduce`/`filter` count of `VERIFIED` vs non-`VERIFIED`), NOT a new server-side aggregation function or a new field on `ResearchReport`. This keeps `SPEC-RESEARCH-001`'s `ResearchReport` type contract completely untouched (per Out of Scope — AI 파이프라인 알고리즘 변경).

Everything below (UI markup restructuring, SELECT projection expansion, form-state additions) is a mechanical consequence of these three decisions and is unlikely to need independent re-review once §A is approved.

## §C. Technical Approach Summary

- **Idempotency-as-append-only-refinement, not a new subsystem**: both dedup checks (M2) are a single additional `SELECT ... WHERE ...` guard inside the existing write-path functions (`createCase`, `submitReportFeedback`) — no new service, no new queue, no new library. This matches the user's explicit "keep it minimal" instruction and the codebase's existing pattern of DB-backed dynamic validation inside write-path functions (SPEC-FEEDBACK-001's own `submit-feedback.ts` step-by-step validation is the direct precedent this milestone extends).
- **UI-first, schema-minimal**: 4 of 6 requirement groups (A, C, D, F) are pure UI/markup/query-projection changes with ZERO schema impact. Only group B (idempotency) touches `lib/db/schema.ts`, and that touch is two nullable, additive columns — no existing column, type, or constraint is altered.
- **Client-generated nonce, server-enforced uniqueness**: the nonce is generated client-side (`crypto.randomUUID()`, already a browser-native API, no new dependency) once per form mount and travels with the request; the server is the sole enforcement point (a DB-level unique index + a pre-insert existence check), so a malicious or buggy client cannot bypass the guard by omitting a nonce more than once per legitimate submission.

## §D. Risks

1. **Nullable-unique-index NULL semantics (SQLite/Turso-libSQL)** — resolved in §A decision 1 (iteration-2 fix-up; formerly an open clarification question). SQLite's documented behavior — "For the purposes of UNIQUE constraints, NULL values are considered distinct from all other values, including other NULLs" (sqlite.org/lang_createtable.html) — treats multiple `NULL` values in a unique-indexed column as NOT conflicting, and this project's `turso` (libSQL) dialect inherits the same semantics, which is the desired behavior here (a caller that never sends a nonce should never collide with itself). Residual risk (low): mechanical confirmation against the generated migration + a fixture test with two `NULL`-nonce inserts (M1/M6) is still scheduled to catch any drizzle-kit-specific code-generation surprise, but the semantics themselves are no longer in question.
2. **Append-only regression (feedback dedup)** — the single highest-risk item in this SPEC (§B M2 constraint). A dedup query written as `(reportId, userId)` instead of `(reportId, userId, submissionNonce)` would silently reintroduce a uniqueness constraint SPEC-FEEDBACK-001 explicitly rejected, breaking the "initial review + later outcome confirmation" workflow. Mitigation: the explicit regression test in M6 (two different nonces, same reportId+userId, both must insert) is mandatory, not optional.
3. **`EvidenceDisplay` interface duplication** (`page.tsx` and `feedback-form.tsx` each define their own local `EvidenceDisplay` interface) — REQ-PILOT-UX-006 requires both to gain the same two fields. Risk: updating one and forgetting the other produces an inconsistent evidence display between the two screens. Mitigation: since both files already duplicate this interface (pre-existing pattern, not introduced by this SPEC), M3 explicitly calls out editing both; self-review before completion should grep both files for `EvidenceDisplay` to confirm parity. Extracting a shared type into `lib/pipeline/types.ts` or a new shared module is a reasonable follow-up but is NOT required by this SPEC (scope discipline — the existing duplication pattern is preserved, not refactored away).
4. **`submissionNonce` on `caseInputSchema`** — if the nonce is added directly into the Zod-validated `caseInputSchema` (`lib/validation/case-input.ts`) rather than kept as a separate parameter, it risks being persisted into the `cases.input` JSON blob and later echoed back through `report.caseSummary` or similar paths, which is an unintended surface for an internal implementation detail (not a PII risk, but a data-hygiene one). Mitigation: M2 explicitly recommends a separate function parameter over schema inclusion; this is an implementer's-call note (non-blocking, not a formal open clarification question) since either approach is safe as long as the nonce is excluded from `report.caseSummary`.
