# Design — SPEC-SCAFFOLD-001 (Light — 최소 UI 서피스만)

> 이 SPEC은 scaffold+아키텍처 구축이 목적이며 폴리시된 UI/UX 디자인은 범위 밖이다(spec.md §4 Out of Scope — UI/UX 고도화). 이 design.md는 파이프라인을 수동 시연하기 위한 **최소 UI 서피스 2개(사건 입력, 리포트 뷰)**만 다루며, 전면적인 디자인 시스템 탐색은 수행하지 않는다. 전체 UI/UX 디자인은 `product.md` §Roadmap의 후속 SPEC("사건 입력 폼 UI (민감정보 입력 차단 검증 포함)", "Research Report 렌더링 UI 및 리포트 데이터 모델")으로 이연한다.

## §1. UI 서피스 범위

이번 SPEC에서 다루는 화면은 정확히 3개다:

1. `app/login/` — 초대받은 테스터 로그인 화면
2. `app/cases/new/` — 사건 입력 폼
3. `app/cases/[caseId]/` — 사건 상세 + 리서치 리포트 뷰

컴포넌트는 shadcn/ui 기본값(Button, Card, Form, Input, Label)을 그대로 사용하며, 커스텀 디자인 토큰이나 별도 브랜드 시스템을 도입하지 않는다.

## §2. 사건 입력 폼 (`app/cases/new/`)

- 목적: 비식별 보험 사건 정보(상해/질병 경위, 진단명, 장해 부위 등)를 입력받아 파이프라인을 트리거한다.
- 필드: `lib/validation/case-input.ts`의 Zod 스키마가 정의하는 필드 집합을 그대로 폼 필드로 매핑한다(주민번호/전화번호/상세주소/의료기록 원본 필드는 애초에 폼에 존재하지 않는다).
- 상호작용: shadcn/ui `Form` + `Input`/`Textarea` 조합의 클라이언트 컴포넌트, 서버 컴포넌트인 페이지 셸 내부에 배치.
- 제출 시 `app/api/cases/` route handler를 호출하고, 성공 시 생성된 `caseId`로 `/cases/[caseId]`로 이동한다.
- 검증 실패(PII 형식 감지 등) 시 필드 단위 에러 메시지를 표시한다(폴리시된 UX는 후속 SPEC).

## §3. 사건 상세 + 리포트 뷰 (`app/cases/[caseId]/`)

- 목적: 파이프라인이 생성한 Research Report를 조회한다 — 추가 검토 담보 목록, 관련 근거자료, 예상 반대 논리, 추가 필요자료 4개 섹션을 단순 리스트/카드 형태로 렌더링한다.
- `owner_user_id` 스코핑: 서버 컴포넌트에서 `lib/auth/session.ts`로 현재 사용자를 조회하고, 조회 쿼리에 항상 `owner_user_id` 필터를 적용한다. 소유하지 않은 사건에 접근 시 404를 반환한다.
- 전문가 피드백 저장을 위한 최소 입력(텍스트 영역 + 제출 버튼) — 데이터 모델(`feedback` 테이블)까지만 이번 SPEC 범위이며, 피드백 UI 자체의 고도화는 후속 SPEC.
- 리포트 렌더링은 정적 서버 컴포넌트로 충분하며, 별도 클라이언트 상태 관리 라이브러리를 도입하지 않는다.

## §4. 로그인 화면 (`app/login/`)

- 목적: Better Auth 초대 전용 allowlist 인증 진입점.
- 최소 폼(이메일 + 비밀번호 또는 매직 링크 트리거 버튼 — 최종 provider 형태는 M2 구현 시 `lib/auth/config.ts`의 결정을 따른다).
- allowlist 미등록 사용자의 로그인 시도는 일반적인 인증 실패 메시지로 처리한다(계정 존재 여부를 노출하지 않는다).

## §5. 명시적 디자인 결정 유보 사항

다음 항목은 이번 SPEC에서 결정하지 않으며, 후속 UI/UX SPEC에서 다룬다:

- 색상 팔레트, 타이포그래피, 반응형 레이아웃 세부 규칙
- 리포트 뷰의 정보 계층 구조(담보/근거/반대논리/추가자료 4개 섹션 간의 시각적 우선순위)
- 사건 입력 폼의 단계별(wizard) 흐름 여부
- 접근성(a11y) 세부 감사 — shadcn/ui 기본 컴포넌트의 접근성 기본값에 의존한다.
