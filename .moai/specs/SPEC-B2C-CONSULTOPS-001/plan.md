# Plan — SPEC-B2C-CONSULTOPS-001

## 결정 우선순위 (Decision Review Priority)

되돌리기 어렵고 다른 결정에 영향이 큰 순서다. 리뷰 시 이 순서로 확인하기를 권장한다. 마일스톤(§F)도 결정 → 사용자 노출 문구·도착지(되돌리기 어려움) → 절차·기록 → 시크릿·환경 절차 → 시험 수행 순으로 놓았다.

1. **D-OPS-12 내부 시험의 범위와 면제 항목**, **D-OPS-11 증거 보관 위치**: D-OPS-12는 증거 표 I 열의 `D-OPS-12` 칸이 면제로 바뀌는지(AC-002 (바)(사)는 결정 전의 fail-closed 규칙과 면제 뒤의 동작을 시험하므로 이 결정을 기다리지 않는다)를, D-OPS-11은 런북 기록 표의 보관 위치 칸(AC-001의 선결)을 정한다. 저장소가 공개라서 한 번 커밋한 기록은 되돌리기 어렵다. D-OPS-12 전에는 `D-OPS-12` 칸이 필수로 취급되므로 결정이 늦을수록 내부 시험 문턱이 높아진다(fail-closed).
2. **D-OPS-01 동의·정책 문구와 버전 식별**, **D-OPS-02 보존·삭제**: 사용자가 보는 문구와 저장 계약에 걸린다(N2).
3. **D-OPS-03 담당 창구·약속·상태**, **D-OPS-04 도착지**, **D-OPS-05 연락처 표시**: 사용자 화면과 `.pen`·CONSULT-001 계약에 걸린다(N1, N3~N5).
4. **D-OPS-07 시크릿**, **D-OPS-08 PM2 재시작 전략**, **D-OPS-09 전제**, **D-OPS-10 시험 행**: 운영 절차이며 되돌리기 쉬운 편이다. 단 D-OPS-08은 D-OPS-07의 보관 위치를 정한다.
5. **D-OPS-06 링크·미준비 안내**: 문자열 교체 수준이다.

### 리스크

- **공개 저장소에 기록 커밋**: 증거 기록·서명 기록에 실제 연락처(이용자·담당 창구·서명자)·시크릿·법적 판단 세부가 들어가면 공개된다(F-21). D-OPS-11 전에는 기록을 커밋하지 않는다. REQ-012가 이 값들을 이 저장소의 추적 파일에 담지 못하게 하는 층이고 AC-012가 canary와 추적 여부 확인으로 점검한다. 알려지지 않은 실제 값의 유출은 canary가 못 본다(AC-012의 "보지 못하는 것").
- **정책 준비 = API 공개**: `CONSULT_POLICY_READY=true`이면 UI 도달과 무관하게 API가 인증 없이 열린다(F-03). 내부 시험도 같은 노출을 갖는다(E-08, N8). 내부 시험을 운영 호스트에서 하면 `true` 설정 단계를 이미 거친 상태라 I와 G를 가르는 집행 지점이 이 SPEC에 없다 — 이행 게이트는 LAUNCH 소유다(§2.4, REQ-002, N7).
- **문구 변경의 파급**: 연락 약속 문구는 `.pen`·`design/exports`·`visual:verify`와 걸려 있다(N4). 03-D 연락처 표시와 03-C 서술은 CONSULT-001 REQ·AC와 겹친다(N1, N5).
- **스키마 변경**: D-OPS-02·03(c)·10이 새 열을 요구하면 `consultations` 변경과 운영 DB 마이그레이션이 필요하고 사람의 별도 승인이 먼저다(N2).
- **PM2 재시작 미검증**: 활성화·롤백이 모두 재시작에 의존하는데 환경 재읽기가 미검증이다(F-16). 읽지 못하는 전략으로 롤백하면 롤백이 일어나지 않는다. 또 `deploy.yml:61`의 평범한 `pm2 restart`가 `main` push마다 일어나므로(F-13) 켜진·롤백된 상태가 이후 배포 뒤에도 유지되는지도 미검증이다. 그래서 REQ-013이 활성화의 선행 조건이고 E-03이 두 관측을 함께 담는다.
- **READY의 낡음**: 한 번 관측한 증거 항목이 이후 배포·환경 변경·재시작·플래그 변경으로 사실이 아니게 되어도 `READY`로 남으면 게이트(REQ-002)가 무의미해진다. §2.4가 항목별 무효화 사건으로 이를 닫지만, 점검기는 사건 발생을 스스로 감지하지 못하고 절차 단계가 상태를 되돌려야 한다(REQ-001, AC-002·AC-001 (5)). 코드 종류 항목의 대상은 커밋이 아니라 덮는 파일 집합의 내용이므로 `main` push마다 배포되더라도(F-13) 증거 기록만 바꾸는 커밋은 EV-1이 아니다(§2.4).
- **ENGINE-001과의 겹침**: 같은 계약·같은 DB에 변경이 날 수 있다(N6). 03 상담의 일반 사용자 대상 사용은 ENGINE의 "실제 결과"를 기다리며(E-17, F-20), `resultId`의 서버 검증 여부는 ENGINE의 D-ENGINE-05가 정하므로 이 SPEC은 그 어느 쪽도 가정하지 않는다.
- **점검기의 한계**: 증거 표 점검기(AC-002)는 절차를 막을 뿐 운영 호스트에서 환경 값을 손으로 바꾸는 것을 막지 못한다. 이 한계를 AC에 적었고 추가 런타임 게이트는 이 SPEC의 범위가 아니다.
- **PR CI 없음**: 병합 전 자동 검증이 없다(F-19). 이 SPEC의 시험은 로컬 실행 증거로 제출된다.

## §G. Anti-Patterns

- 담당 창구·기한·상태 이름·문구·보존 기간을 이 SPEC이나 코드가 임의로 정하지 않는다(결정 대기).
- 확정되지 않은 문구를 확정된 것처럼 표시하지 않는다. 임시 본문을 확정 문구로 간주하지 않는다.
- `CONSULT_POLICY_READY`를 이 SPEC의 산출물에서 켜지 않는다(REQ-003).
- 운영 호스트에서 재읽기가 관측되지 않은 재시작 전략으로 활성화·롤백하지 않는다(REQ-013).
- 시크릿 값·실제 연락처를 기록·로그·채팅에 남기지 않는다(REQ-012). `pm2 jlist` 전체 출력처럼 환경 값이 나오는 명령을 절차에 넣지 않는다.
- "배포 완료"를 "일반 공개 가능"으로 서술하지 않는다(REQ-001).
- 일반 공개 증거에서 ENGINE-001 소유 증거(E-17)를 이 SPEC이 대신 판정하지 않고, ENGINE-001의 D-ENGINE-05(`resultId` 서버 검증 여부)를 선점하지 않는다.
- 이미 일어난 관측을 무효화 사건 뒤에도 `READY`로 두지 않는다. 미해소 `D-OPS-12` 칸을 면제로 읽지 않는다(§2.4).
- 결정 대기 항목을 요구사항 문구로 먼저 정하지 않는다. 옵션이 요구사항을 바꾸게 되면 그 요구사항의 amendment를 충돌(N1~N6)로 기록한다.
- `deploy.yml`의 smoke 문구를 이 SPEC에서 바꾸지 않는다(LAUNCH 소유, 상담 플래그는 `/` smoke에 영향 없음 — F-14).
